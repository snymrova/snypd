## 2. Scope

**In (v0.1) — 13 primitives**
`cover, tldr, callout, pullquote, stat, stat-row, figure, faq, steps, cta` + **`chart`, `diagram`, `flow`**.

- `chart` — `type: bar | line | area | donut | lollipop`, `data:` inline YAML or `src:` file, **`source` required**, `caption`. Rendered to inline SVG by `packages/viz` (own code, no D3/Chart.js). Theme supplies only tokens (palette, font, grid colour); the spec owns geometry so every theme's charts read as one system.
- `diagram` — box-and-arrow: `nodes`, `edges`, `direction: lr | tb`. Layered layout (longest-path ranking + barycentre ordering — a small Sugiyama, ~300 lines). Deterministic; layout cached by content hash so a second build costs a `copyFile`.
- `flow` — ordered steps with branches (`yes/no`, `then`), a constrained sugar over `diagram` that agents can write without thinking about coordinates. Emits `HowTo` schema like `steps`.
- All three: build-time SVG only, `<svg role="img" aria-label>` + a `<title>`/`<desc>`, a `<figcaption>`, and a **text fallback** (data table / step list) emitted into the `.md` twin so agents reading the twin get the data, not a picture.

**Also in:** YAML layering; `post / page / author`; `category / tag`; statuses `draft → published → trashed`; lint (rules 0–11, below); SQLite index; git ops (draft branch, principal trailer); static build with incremental cache, `.md` twins, `llms.txt`, RSS, sitemap, JSON API; tokens → CSS vars; MCP stdio with resources `config, spec/*, theme/*, content/*, lint/*, bench/latest`, tools `content.*` + `find_tools` always listed, with `theme` / `site` / `bench` one-tool-per-namespace in the catalogue behind it — **decision 38 replaced the flat per-verb surface this line used to describe, and every *read* in it is now a resource, not a tool**; prompts `get-started`, `write-post`; themes `base`, `editorial`; bench (speed, visual, agent); binaries.

**Lint (12 rules, 0–11 — `packages/core/src/content/lint.ts` carries the table):** frontmatter schema · unknown block · required / invalid / unknown prop and slot limit · unsourced `stat`/`chart` · image without alt · dead internal link · heading skip · stale `updated` · slop-phrase list · callout density · slug change without redirect (rule 10, a real remedy since S16 — decision 39) · a tag no other post uses. Plus the **≤ 40-node graph cap** (readability + render budget, §3.4).

**Cut to v0.2:** `gallery` (needs media manifest) · `review`/`scheduled` statuses · Pagefind · `render_preview` screenshots (`Bun.WebView`) · `history.*` / `taxonomy.*` / `media.*` tools · Mermaid *import* (we own the syntax; a `mermaid → diagram` converter is a v0.2 plugin) · Windows binary.

## 3. Speed strategy

1. **Bench ships before the renderer.** Session 1 measures a stub that copies markdown to `dist/`. Every later session diffs against `main` with `bench.compare`; > 10 % regression on cold build, incremental, cold start or per-primitive visual time is a failed session, not a warning.
2. **Corpora checked in, session 2**: 100 / 1k / 10k synthetic posts; every 5th post carries a chart, every 10th a diagram, every 20th a flow with ≥ 15 nodes.
3. **CI budgets = 80 % of published budgets**, and **CI is where a number becomes comparable** (S18d′). Every session
   log from S5 to S18d explains a metric away with a load average — this box runs at 10–20 on four cores from other
   work, and a full bench under it reads 1.5–3× slow across every lane, so most sessions published nothing. The
   workflow that had never run turns out to be the fix: a runner is idle by construction, identical run to run, and
   somebody else's hardware, which is the definition of reproducible. It reads *faster* than the author's box at its
   quietest — `mcp.coldStart.binary` 20.9 ms against a best-ever local 28.7, `build.cold.100` 280 ms against 495 — so
   the budgets were being defended against noise, not against the product. **`bench/latest.md` is the CI run from
   now on**; a local run is a probe, and one is not published unless it is the only one available and its load is
   stated beside it. This also makes S20's "final speed pass" a diff between two CI runs rather than an argument
   about two boxes.
4. **Pre-committed speed design:**
   - Route cache key = `hash(content) + hash(theme graph) + hash(config subset)` in SQLite; unchanged routes are copied.
   - mdast parsed once per file hash, shared by lint, `suggest_blocks`, twins, render.
   - **Viz cache**: each chart/diagram SVG is keyed by `hash(props + tokens)`; a token change rebuilds only SVGs, not layout — layout (node positions) is cached separately from paint.
   - Diagram layout budget enforced by lint (≤ 40 nodes), so Sugiyama stays O(small).
   - `renderToString`, no hydration, no client React. Themes may not add JS to `chart`/`diagram`/`flow` in v0.1.
   - MCP: lazy-load renderer and viz so `initialize` answers cold in ≤ 50 ms; bytecode-compiled binary.
   - `.md` twin = byte copy of source + resolved frontmatter + generated text fallbacks for viz blocks.
5. **remark vs `Bun.markdown` measured weekly** on 10k; parser switch is a v0.2 spike only.
6. **Bun-native APIs allowed in v0.1:** `bun:sqlite`, `Bun.serve`, `bun build --compile`. Nothing else, behind `packages/runtime/` with a Node CI lane.

## 3b. Deployment model

```
Claude Code ──MCP──▶ snypd serve (local, incremental builds, instant preview)
                        │ commits with Snypd-Principal trailer
                        ▼
                   git push ──▶ GitHub ──▶ host runs `snypd build` ──▶ dist/ served
```

- **Snypd never talks to a host.** It writes files and git. The host's only job: on push, run `snypd build`, serve `dist/`. Pushing `snypd/drafts` gets one preview URL from the host — every draft in flight, on one staging site; that is the v0.1 review page, free (S17b: one branch, not one per item).
- **Two first-class hosts:** `snypd init --deploy cloudflare | vercel` writes the config (`wrangler.toml` / `vercel.json`), a `.github/workflows/snypd.yml` that runs `snypd bench` on PRs, and the build command `npx -y @snypd/cli@<version> build` — pinned, installed from the registry, and **not** the `curl -fsSL … | sh` this line specified until S18d′ refused it (decision 68). Anything that can run a binary and serve a folder also works; nothing in core is host-specific.
- **Local is the fast path.** `snypd serve --preview` renders from the SQLite watcher (≤ 300 ms incremental, ≤ 50 ms TTFB). `snypd build` locally is the same code the host runs, so the published build number is the number the host sees.
- **Push is explicit.** `content.publish` = merge to `main` locally. `site.push` is a separate tool with `destructiveHint`, off for Contributor tokens. A prompt-injected agent cannot put anything on the internet alone.
- Not in v1: Snypd holding host credentials or calling deploy APIs.

## 4. Schedule — Claude Code sessions, not calendar weeks

Unit of work = one autonomous session (~2–4 h wall clock, one PR, bench diff attached). Sunny reviews PRs and runs the gates. Estimated **29 sessions** (S19 split in the S18 audit; S18 split by the compile spike that opened S18a, and again by the first run — S18d–S18g, docs/08, which also unparks S18b″ as S18d′); at 2 sessions/day that is **~15 working days**, at 1/day ~6 weeks. Gates don't move; the calendar does.

Each session opens with: read `docs/*.md` + `bench/latest.md`, run `bun test && snypd bench --quick`, then work. Each session closes with: tests green, bench diff in PR body, `07` §5 log updated.

## 7. Decisions in this plan (override 06 where they conflict)
1. Engineer = Claude Code in bounded sessions; 24 sessions, three gates, calendar floats.
2. **13 primitives**: `chart`, `diagram`, `flow` are v0.1; `gallery` is not.
3. Viz = own `packages/viz`, build-time SVG, zero JS, spec-owned geometry, theme-owned palette. No D3, no Mermaid runtime.
4. New gate **D3** with per-primitive render-time and byte budgets.
5. Pagefind, `review`/`scheduled`, screenshots → v0.2.
6. CI budgets = 80 % of published; > 10 % regression fails the session.
7. Bun-native surface in v0.1 = `bun:sqlite`, `Bun.serve`, `--compile` only.
8. Dogfood = `snypd.rocks`, greenfield, content authored via Snypd; `/bench` page is the public benchmark.
9. npm scope `@snypd/*`; product name decided at launch.
10. Deploy = git push → host builds. Cloudflare Pages and Vercel both first-class via `snypd init --deploy`; `site.push` is explicit and off for Contributor tokens. **Amended in the S18 audit:** "host previews are the v0.1 review UI" was written before S11 shipped the local review page, which is the one the kill test actually drives (`packages/bench/agent/run.ts:58`). The **local Desk** is the v0.1 review UI (decision 44); the host preview of `snypd/drafts` is the shareable one, for a reviewer who does not run the repo.
11. **No `@modelcontextprotocol/sdk` at runtime** (S4): it costs ~140 ms before `initialize` can be answered, 3× the cold-start budget. `@snypd/mcp` ships its own JSON-RPC stdio layer (`protocol.ts`, zero imports) and mirrors the SDK's result types locally; the SDK stays a devDependency for reference. Revisit only if the streamable-HTTP + OAuth transport (docs/03) proves cheaper to adopt than to write.
12. **`js-yaml` on the content path, `yaml` on the config path** (S5): the `yaml` package costs ≈ 1.2 ms per call in Bun 1.4 (15× js-yaml, 40× `Bun.YAML`), which is 1.2 s per 1k frontmatters. Config layering keeps `yaml` for its CST line numbers (provenance, decision 7 keeps `Bun.YAML` out); frontmatter and `chart`/`diagram`/`flow` bodies use `js-yaml`, which needs no provenance. Both accept the same YAML 1.2 core subset that the spec examples use.
13. **The index is disposable, so it is not durable** (S6): `.snypd/index.sqlite` runs `journal_mode = MEMORY`, `synchronous = OFF` — creating it costs 3 ms instead of ~0.5 s of fsyncs on a loaded box, and a corrupt index is deleted and rebuilt from git, never repaired. The parsed-mdast cache lives in the same file (one transaction per build, no per-document files). WAL waits for S11's concurrent reader.
14. **Themes are string-rendering TSX with no framework** (S6): `@snypd/render/jsx-runtime` is ~60 lines — strings escape, `Html` passes through, attributes drop on `false`/`null`. A theme is `theme.yaml` + `layouts/<name>.tsx` + one `.tsx` per primitive; `base` implements all 13 with semantic HTML, one class per primitive, zero CSS and zero JS. `chart`/`diagram`/`flow` render their spec fallbacks (a table, a node/edge list, a step list) until S8–S10.
15. **The reduction is report-only, because as defined it rewards bloat** (S7, ~~S13~~ **rewritten S13 with the measurement in hand**): the metric is `1 − tokens(twin)/tokens(own html)`, and S7 deferred its 85 % budget to a styled theme on the grounds that `base` "has no chrome to save". The editorial lane now exists and says otherwise: **md 510 vs HTML 1,371 → 62.8 %**, against `base`'s 62.5 %. Editorial adds eleven tokens of HTML, because S12's whole design is that it is tokens and a stylesheet with zero markup of its own. To reach 85 % at a 510-token post the HTML would have to carry ≈ 2,000 tokens of chrome, and the requirement *grows* with post length — so the budget is only reachable by making the HTML worse, and inlining critical CSS in S14 would "improve" it. A metric whose budget is passed by regressing the product is the wrong metric to gate. **`tokens.page.md ≤ 2,500` is the gated agent-cost line** — it is what an agent's context window actually pays, it has been gated since S2, and it is 20 % of budget. The reduction stays in every report as `tokens.page.reduction[.editorial]`, report-only, described as what it is: how thin this theme's HTML already is. docs/05's 92 % claim is about a real CMS's HTML, not ours, and belongs to a comparator we do not have and would have to construct — a strawman you beat is weak evidence. Everything the budget existed to guarantee — the twin exists, is byte-identical to the source, is linked, and is negotiable — is `surface.completeness`, enforced at 100 % since S7.

16. **`chart` reads its rows from the post, not from a file** (S8): the spec declares `src=` (rows in a YAML/JSON file) and lint accepts it, but v0.1 does not read it. A route's cache key hashes the post, the theme and the config — a chart whose numbers live in another file would not rebuild when those numbers changed, and making it correct means teaching the *plan* phase which data files a route depends on (it does not parse posts at plan time today). Body YAML and `data=` are resolved into the block by the content pipeline instead, so they are cached with the post and the key stays honest. `src=` is a lint warning with the fix in the hint, never a silently empty figure. Revisit with the S11 content tools, where a post already declares its dependencies.
17. **Viz owns geometry down to the axis orientation** (S8): `bar` and `lollipop` are horizontal, `line`/`area` vertical, `area` includes 0 and `line` does not, ticks are 1 / 2 / 5 × 10ⁿ. A theme supplies `--color-viz-*` and type; it cannot move a point. This is decision 3 made concrete, and it is what lets `snypd bench` state one render/byte budget per primitive that every theme inherits (D3).

18. **An edge label rides its own line, haloed in `Canvas`** (S9): the label of a `diagram` edge sits on the longest straight run of that edge with a 3px halo painted in `var(--color-viz-halo, Canvas)`. Offsetting labels clear of the lines was tried first and has nowhere to go — three edges routinely share one 54px gap, and a box is the only other place to put the text. `Canvas` is the CSS system colour for the page's own background and resolves per element's `color-scheme`, so the halo is white on a light page and dark on a dark one **with no token declared**, which is the only halo that does not force the theme to tell viz what colour the page is. Verified in headless Chrome on a `color-scheme: dark` surface.

19. **A forward jump's target sits out of the straight line** (S10): in `flow`, a named step that only *earlier* steps `then:` into is a branch landing — the straight path steps over it, and only the branch that names it goes there. A jump *back* to an earlier step is a retry loop and changes nothing about the line. The spec's own example is the argument: `no: { then: fix }` puts the fix out of line, and under any simpler rule ("a branch rejoins the next item in the list") the `yes` branch falls into "fix the reported rule" on its way past — the picture would say the opposite of the procedure. The alternative rules were tried and each breaks a case this one does not: *always step over a named step* kills the retry loop (`- { id: lint, do: Run lint }` would drop out of a flow that loops back to it), and *never step over* is the wrong picture above. Direction of the jump is the only signal that separates the two, and it is one line of code. The rule is in `flow.yaml`'s slot description, so an agent reads it with the primitive.
20. **A decision is a rhombus, and viz owns a fourth node kind to draw it** (S10): `NodeKind` gains `diamond`, but `NODE_KINDS` — the list a `diagram` body may name and lint checks against — stays `box | rounded | pill`. Only the `flow` desugar produces a diamond. Sizing follows from the shape: a rhombus only holds text satisfying `|x|/(w/2) + |y|/(h/2) ≤ 1`, so a decision is ≈ 1.6× as wide and ≈ 2.6× as tall as the box the same words would need, and it wraps at 160px rather than 172 — widening is cheap (a rank is as tall as its tallest node either way), heightening pushes ranks apart. Edges attach at the apex with **no fan**: a diamond has no flat side, and an edge attaching a third of the way along one would end in the white space beside the point. Steps are `rounded`, so a flow does not read as a diagram with different words.

21. **A draft branch is per item, named `snypd/draft-<type>-<slug>`, and records the branch it was cut from** (S11): docs/02 §7 wrote `snypd/draft-<slug>`, but a slug is unique *within* a type — a `post` and a `page` both called `about` would share one branch, and publishing either would merge the other's words. The base goes in `branch.<name>.snypdBase`, so `content.publish` merges back where the draft started rather than wherever HEAD happens to be when it is called. Only the paths a write touched are staged, and a tree carrying anyone else's uncommitted work refuses the branch switch instead of dragging it along.

22. **An approval names a content hash and lives in `.snypd/approvals.json`, not in an index** (S11): the preview server keeps its *own* route cache (`preview.sqlite`) so rendering drafts cannot disturb `dist/`, so "store it in the index" would have meant storing it in the wrong one — the first cut did exactly that, and publish refused an approval that had just been granted. A route cache and a human's decision are unrelated anyway, and a file is readable by the person who made it. The hash is what makes it an approval of *those words*: edit after approving and the publish is refused with the reason. Losing the file can only ever refuse a publish, never grant one.

23. **A site is git-backed only when the site root is the git top level** (S11): `git rev-parse --show-toplevel` must equal the root. A corpus at `corpora/100` is inside the snypd repo, so under any looser rule every benchmark write would commit into snypd itself. Sites that are not their own repo get the file writes and no commits — no half-measure, and nothing to configure.

24. **A theme is a chain, and a slot is looked up along it** (S12): `extends:` was in the contract, in the
`ThemeYaml` type and in `base`'s own personality since S6, and `loadTheme` never read it — so the floor theme
advertised an inheritance that did not exist. Resolution is **per slot, not per theme**: the nearest ancestor
declaring a layout or primitive wins, and each path resolves against *that* theme's dir. Flattening the chain
into one map was the obvious first design and it cannot work — `./primitives/callout.tsx` means nothing without
the theme that wrote the line, and a merged map has thrown that away. Consequences that are not optional:
`themeHash` covers every dir in the chain, or a child inheriting a primitive serves stale HTML when the parent
changes; the chain is resolved once in `@snypd/core` and carried on the theme layer, so the config layer and the
loader cannot drift; and a cycle truncates and reports rather than throwing, like every other config error.
The payoff is the whole point of a floor theme: `editorial` is `theme.yaml` + one stylesheet with **zero `.tsx`
of its own**, and it covers 13/13 primitives. Had `base` not kept one `snypd-<name>` class per primitive, none
of this would have been reachable from CSS alone.

25. **`editorial` gets dark mode from tokens, not from a media query** (S12): every colour token is a
`light-dark()` pair and `theme.css` declares `color-scheme: light dark`. A `@media (prefers-color-scheme: dark)`
block would have meant a second copy of the palette in a file the theme's own tokens cannot reach — the
site could override `color.accent` in `snypd.yaml` and change only the light half. It also settles viz for
free: decision 18 paints the label halo in `Canvas`, which resolves per `color-scheme`, so declaring the
scheme once is what makes every diagram legible on a dark page. Cost: 0 bytes of CSS and 0 JS.

26. **The browser suite drives Chrome itself, and owns no Lighthouse** (S13): `snypd bench page` is
`packages/bench/src/cdp.ts` — a WebSocket carrying `{id, method, params, sessionId}`, which is the whole of
the DevTools protocol — plus `axe-core`, a dev dependency with zero transitive packages. Lighthouse was
installed, measured at **114 packages**, and removed: its accessibility category *is* axe, its performance
half is a weighted curve over vitals that an unthrottled localhost cannot honestly simulate, and `snypd
bench` is reachable from the CLI that S18 compiles into one binary. The same instinct as decision 11. The
two things the exit criteria actually assert are gated — `page.js.kb` at **0** and `page.a11y.violations`
at **0** — and the vitals are reported beside them. A composite score, when someone wants to quote one,
comes from `bunx lighthouse` against the same built site: a number to publish, not a dependency to carry.

27. **`content/media/` is copied verbatim, and the build reads each file's intrinsic size** (S13): before
this, a site could not ship an image at all — `figure` is a spec primitive with a required `src`, and
nothing in the renderer put a byte in `dist/` that was not a route or a generated artefact. The copy is a
plan item like any other, keyed on size + mtime, so an unchanged image is not recopied. The *sizes* are the
less obvious half: `figure` and `cover` emit `width`/`height` from them, because an image with no reserved
box is Cumulative Layout Shift, and the theme cannot know the dimensions while the build already has the
file open. `media.ts` reads five formats from their headers (PNG, JPEG, GIF, WebP, SVG) in 64 KB, never the
whole photograph. The sizes go into the route key: a replaced image with new dimensions re-renders the
pages that place it, exactly as a theme edit does — a test caught that being wrong. This is the seed of
docs/02's `media.yaml`, not the manifest: no blurhash, no credit, no derivatives, no licence lint.

28. **A type that declares no `status` field has no lifecycle, so it is public** (S13): status came from
`frontmatter.status ?? initialStatus`, and `initialStatus` is `draft`. The built-in `author` type declares
no `status` field — so every author was permanently a draft, the `author` layout that `base` ships could
never render, and the only way to publish one was a frontmatter key that lint calls unknown. Found by the
theme fixture, which is the first site in this repo to have an author. `defaultStatus(cfg, type)` now asks
whether the type has the field at all; if it does not, the file is public at whatever status the site says
public means. A type gets a lifecycle by declaring one.

29. **The preview bundles the theme per change** (S13, closing an S11 debt): `loadTheme({ bundle: true })`
runs `Bun.build` over the chain's entry files with `@snypd/*` external, and imports the output. Busting the
import URL — what S11 shipped — re-imports the entry file, but a file that entry imports *statically*
(`./shell`, `./entries`) still comes from Bun's module cache, so editing the shell re-rendered every route
with the old component and printed a warning instead of a page. Externalising `@snypd/*` is not an
optimisation: `Html` is a class, and a layout returning a differently-bundled `Html` is not the one the
renderer accepts. `snypd build` is one process per run and does not ask for any of this, so it pays
nothing; `preview.ttfb` is unchanged, because the bundle happens when the theme hash moves, not per request.

30. **A `type: markdown` prop is rendered as markdown, and only the display copy goes through it** (S14):
five props in the spec are declared `markdown` — `caption` on `figure`, `chart`, `diagram` and `flow`, and
`body` on `cta` — and every one of them reached the page as literal text, so the theme fixture shipped a
figcaption reading ``The `.md` twin is the source file.`` with the backticks in it. `inline()` renders them
without a `<p>`, because the value lands inside a `<figcaption>`. The *plain string* still goes to
`@snypd/viz` for the SVG's `<title>`, where markup would be read out loud. A string containing none of
`` ` * _ [ ] < > & \ ~ ! `` and no block opener skips the parser entirely and is escaped instead — the two
paths are asserted byte-identical, and the parse costs ~0.5 ms against ~0 for the test, which on a 100-post
build with three captions a post is the difference between +150 ms and nothing.

31. **The stylesheet is minified, and never inlined** (S14): the S14 row said "critical CSS", and the
classic form of it — a critical slice inlined, the rest fetched with `media="print" onload="this.media"` —
is unavailable here, because that `onload` is JavaScript and `page.js.kb` counts `on*` handlers against a
budget of 0. Inlining the *whole* sheet is possible and is refused: it would take `tokens.page.html` from
~1,390 to ~4,500 on every page, tripling the token cost of the thing this project exists to make cheap, to
save one request on a sheet the browser caches for the whole site. What is real is minification —
comments and indentation are 2.2 KB of `editorial`'s 12.6 KB and 1.1 KB of the 3.9 KB a host sends after
gzip — so `minifyCss` runs on the way out, doing only what cannot change meaning: no `:` (`p :first-child`
is not `p:first-child`), no `+`/`-` (`calc()` needs the spaces), strings scanned rather than regexed over.

32. **Viz keeps the size it was drawn at, and the theme scrolls the container** (S14): `@snypd/viz` owns
the geometry (decision 17), and the type size is part of it — stretching the SVG to the column scales the
labels with it, so a 640 px chart rendered 12 px labels at 6 px on a 390 px phone, and a 449 px diagram blew
up until its labels were larger than the `h1` on a wide screen. The drawing now sits at its intrinsic width,
centred, in a `.snypd-scroll` container with `tabindex="0"` — a scrolling region must be reachable from the
keyboard, and no `role`, because the `<svg role="img">` inside already carries the `<title>` that names it.
The inline `max-width` viz emits became `var(--viz-max-width,100%)`: unset it still clamps to the container,
so `base` — which ships no CSS at all — cannot scroll a phone sideways.

33. **A cover is the page's header, so the renderer lifts a leading one out of the body** (S14): the spec
says "at most one, first in the body … omit it and the theme renders a cover from frontmatter", and the
layout had no way to know one had been written, so a post that declared `::cover` got two title blocks —
the layout's, from frontmatter, and then the author's a few paragraphs down. `page.cover` is the rendered
block and `page.body` is everything after it; the layout uses one or the other and the byline sits under
whichever it was. Only a *leading* cover is lifted: one further down is the author's mistake, lint says so,
and moving it would silently rewrite what they wrote.

34. **The index and the feed list a type that has a `date` field** (S14): the filter was
`type !== "page"` — one exception standing in for a rule — so the moment the fixture gave `author` a layout
(decision 28 made one publishable), an author appeared in the site index and shipped in the RSS feed as an
item with no `pubDate`. Both surfaces are newest-first and a feed item needs a date, so the question is
whether the type declares one. It generalises to a user's own types instead of naming the one type someone
had already noticed.

35. **The detectors live beside the spec but outside the vocabulary** (S15): `suggest_blocks` needs a
scored table of what each primitive looks like in prose someone already wrote. The obvious home was
`primitives/*.yaml`, next to `intent` and `anti-intent` — and it is the wrong one. `snypd://spec/primitives/{name}`
is served byte for byte and every one of the thirteen is inside `tokens.learn`, which sits at 4,639 on the
editorial lane against a CI line of 4,800: thirteen detector blocks would have blown the gate outright. The
deeper reason is the same reason: an agent reading the vocabulary needs to know **how to write a chart**,
not **how snypd spots one**, and making every agent pay for a heuristic table on every session to serve one
tool is the cost this project exists to refuse. `packages/spec/detect/{name}.yaml` is still one YAML file per
primitive with no code, still versioned with the spec, and costs nothing at session start. `tokens.learn` is
unchanged at 4,450 / 4,639.

36. **A suggestion may never introduce a lint error it did not declare** (S15): every suggestion is parsed,
typed and linted *against the document it would land in* before it is returned, and one that breaks the post
is dropped rather than shown. What the prose genuinely cannot supply is a **need**, not a guess — a plain
table has no `source:` in it, and lint rule 3 exists precisely because a number whose origin cannot be
clicked is an opinion. So `chart` declares `needs: source` and `apply` **refuses** it rather than writing
`source="TODO"` into someone's post; `fill` is how a caller meets the need in the same call. The property is
worth more than any tuning, and it earns its keep immediately: it is what caught `flow` never emitting the
`caption` its own spec requires, which no unit test was looking for.

37. **Twenty labelled posts at S15, fifty at S21** (S15): docs/05 says fifty hand-labelled posts and the S15
row says twenty, and the plan does not claim to override 05. Twenty is the *session* gate — enough to hold a
precision line while the detector table is being written — and the corpus grows to fifty for the release
gate in S21, where docs/05's number stands. Seven of the twenty are labelled with **no** upgrade, because
precision measured only on posts that have an answer is not precision, it is a demo.

38. **The tool list is small, and the rest is found** (S16): `tools/list` is paid on every turn, and S15
measured 203 tokens per tool. Docs/03's flat surface — one tool per verb across `theme.* site.* history.*
media.* taxonomy.* jobs.* bench.*` — is ≈ 8,600 tokens an agent pays before writing a word, on top of the
≈ 4,600 it pays to learn the vocabulary. So the surface is split three ways at once. **Listed always:**
`content.*`, the hot path, plus `find_tools`. **Found on demand:** a catalogue (`catalog.ts`) whose schemas
`find_tools` returns in full and which then joins `tools/list`, announced with
`notifications/tools/list_changed`; a catalogue tool is callable whether or not it was ever listed, so a
client that ignores the notification loses nothing but a re-list. **Not tools at all:** every *read* is a
resource (`snypd://theme`, `/tokens`, `/coverage`, `snypd://bench/latest`), which costs nothing until
something reads it. And each namespace is one tool with an `action`, not one per verb — nine `theme.*` tools
is nine descriptions, eight of them re-explaining what a theme is. The whole thing is held by a gated budget,
**`tokens.tools ≤ 3,000` (CI 2,400): measured 2,208 listed, 3,284 for the same catalogue listed rather than
found, against ≈ 8,600 flat.** 3,000 is not a number picked to be comfortably met — it is the measured
surface plus roughly one more hot-path tool, which is the point: the budget, not the taste, is what keeps
`media.*` and `taxonomy.*` from quietly undoing this when they land.

39. **A redirect is a real artefact, so lint rule 10 can stop naming a remedy that did not exist** (S16):
since S6 the rule has warned "route changed … nothing redirects the old URL" and hinted that the fix "lands
in v0.2", which left restoring the slug as the only way to silence it. `site` › set_redirect writes
`site.redirects`, and the build emits **both** forms, because neither alone is portable: `_redirects` (a real
301 on Cloudflare Pages and Netlify) and one page per redirect carrying a meta refresh plus a canonical link
(everywhere else, and for a crawler that ignores the refresh). A redirect whose old route is a page the site
actually builds is dropped rather than shadowing it, and rule 10 goes quiet only for a route a redirect
actually covers. Host-level config (`vercel.json`, headers) stays in S18 with the rest of `--deploy`.

40. **A config write that does not load is rolled back before it is returned** (S16): `site` › set_config
patches `snypd.yaml` through the `yaml` Document API — comments, key order and quoting survive, as they do
for frontmatter (decision 14's sibling) — then re-loads the whole merged config and *restores the file* if
it fails, returning the diagnostics instead. This is the entire reason it is safe to let an agent write
config at all: the worst case of a wrong key is an error message, never a site that no longer loads.

41. **`snypd://theme` is part of learning the site; the palette and the coverage list are not** (S16):
docs/05 has scoped `tokens.learn` to config + spec/primitives + theme since S13, but `theme` only became a
resource in S16 — so the metric had been quietly measuring two of the three. It now reads the same bytes the
server serves (`renderThemeSummary`, in `@snypd/core` precisely so the benchmark and the resource cannot
drift): **4,450 → 4,571 base, 4,775 editorial, of 6,000.** The editorial lane clears the CI line (80 % =
4,800) by ~25 tokens, which is a real risk worth naming: one more primitive in the spec breaches it, and the
fix then is to trim the `spec/primitives` reads in S20's speed pass, not to raise a budget docs/05 owns.
Writing this resource is also what caught `installedThemes` reporting the *default* theme as active when the
caller held a non-default env layer — the editorial lane was being told it was running base.
`snypd://theme/tokens` (4.5 KB) and `/coverage` are deliberately *out* of
that budget — they are read by an agent that has decided to restyle, and charging every session for them
would price a session for work it is not doing.

42. **Isolation moves off the checkout and into the land** (S17b): there is one working tree, so a branch per item can only ever show one draft — and a branch cut from another branch carries that branch's commits when it merges. Both halves of S17's finding are the same mistake, which is using *where HEAD points* as the unit of isolation. `snypd/drafts` is checked out once, at the first write, and never left; `Repo.land(paths, subject)` builds the next `main` commit in a temporary index from the base's tree plus exactly the paths being published, with the base as the commit's only parent. What that buys, precisely: a published item carries no other item's words (tree), an unapproved draft is not in `main`'s history either (ancestry), and an agent's content folder is identical before and after somebody publishes (no checkout). The alternative that keeps a merge — cherry-pick onto `main` — was not taken: it needs the item's commits to be *separable*, which they are not once an agent has fixed two posts in one `suggest_blocks` apply, and it leaves the tree needing a checkout back. `land` refuses a path with uncommitted changes, because an approval names bytes, and it is idempotent, because publish is re-runnable.

43. **Content waits for a human; configuration lands as it is made** (S17b): the approval gate exists so an agent cannot publish *words* nobody has read (docs/03 safety defaults). A theme swap or a retuned token is not words — it is the operator's own instruction, given through the harness, and before S17b it was committed "on the branch that is checked out", which was whichever post had been written last: a theme change could sit on `snypd/draft-post-about` and reach the site only when that post published. A configuration change that takes effect everywhere except on the site is the kind of quiet lie the review page exists to prevent, so `theme`, `set_config` and `set_redirect` commit on the drafts branch and land immediately, and say which commit they landed as. Content still waits. Trashing a *published* item lands the removal for the same reason: the item is being taken off the site, not put on it, and leaving it live until someone publishes the deletion is the failure that matters here. Both are one `git revert` away from undone.

44. **The Desk is the operator's half of the surface, and it may not write content** (S18): `snypd serve
--preview` has served `/_snypd/review/{type}/{slug}` and `/_snypd/approve/{type}/{slug}` since S11
(`packages/render/src/preview.ts:23-24`), and the kill test already drives the approve endpoint as the human
step (`packages/bench/agent/run.ts:58`) — so the operator's surface already exists, is already measured, and
had no name. **Snypd Desk** is that namespace grown up: is a harness connected, what is in flight, what the
theme is, and the one button that pushes. The decision is what it may *not* do. There is no authoring on the
Desk, no theme switcher, no config editor — approving words an agent wrote is not editing them and pushing a
commit is not authoring one, which is precisely how D6's "edited only via MCP" stays literally true with a
web page in the product. The alternative is an admin app, which is what every other CMS ships, and it is
refused for the reason this project exists: a second way to write means every feature is built twice, and the
MCP surface stops being the product the moment there is a better way to use it. `write.ts:21` has said so in
a comment since S11 — *"a page in the site served by `snypd serve --preview`, not an admin app"* — and this
is that comment promoted to a decision before the page gets big enough to argue with it. **Naming:**
"Studio" was the first candidate and was dropped for a specific collision — Sanity Studio is a headless CMS's
*authoring* UI, so the closest reference point in the category promises exactly the feature this decision
refuses. "Desk" is the newsroom word for the position this page occupies: where copy lands and a human
decides whether it runs. The name is doing work — it is the argument against the "New Post" button somebody
proposes in six months.

45. **The Desk is server-rendered and its actions are forms, so it needs no exception** (S18): decision 26
gates `page.js.kb` at 0 and decision 31 refused the standard critical-CSS `onload` trick rather than spend
against it, so the review page was built form-first — approve is a `<form method="post">` and a submit button
(`preview.ts:106`). The Desk follows it. A live status card wants a socket and gets a
`<meta http-equiv="refresh">`: what it reports (has a harness connected, when was the last call, is there
anything to push) moves on the order of seconds and is read once, so the polling a human would not notice is
the polling that costs nothing. A `bench page` carve-out for `_snypd` was the expected shape of this decision
and turned out not to be needed, which is the better outcome — one rule for the whole product beats one rule
and an exemption, and the Desk cannot quietly become an SPA. **The Desk also never touches the `initialize`
path.** §3.4 lazy-loads the renderer so `initialize` answers cold in ≤ 50 ms, and there is no headroom to
spend: `mcp.coldStart` measured 89.7 ms against that budget at S17b. The listener binds after `initialize`
returns, or on first request, never before it — and the Desk inherits `preview.ttfb ≤ 50 ms` (D2) rather than
getting a budget of its own, which means a status card may not shell out to git per request.

46. **Bundled assets are a static barrel, on disk and in the binary — one path, not two** (S18a): the
compile spike (§6) killed the assumption that `import.meta.dir` is enough. Two mechanisms fail inside
`$bunfs` and they fail differently: `readdirSync` cannot list a directory that is not a directory, and
`import(join(dir, name))` never reaches the bundler, so the file is not in the binary to find. The obvious
fix is a `--asset` glob plus an `if (compiled)` branch, and it is refused: two code paths means the binary
runs code the test suite does not, which is exactly how a gate stays green for fifteen sessions while being
false. Instead each asset root gets a **generated barrel of static imports** — `packages/spec/src/assets.ts`
(31 YAMLs as `with { type: "text" }`), one per bundled theme for its 20 `.tsx` — checked in, imported
unconditionally, and used in dev exactly as it is used in the binary. A test regenerates it and asserts no
diff, so adding a primitive without regenerating fails `bun test` rather than only the release. The barrel is
also the extensibility line: **bundled** themes are in it because they ship inside the binary; a **user's**
theme is on their disk, where `readdirSync` and runtime `Bun.build` are correct and stay, so a third-party
theme is not a second-class citizen — it is the case the on-disk loader was always for.

47. **The compiled binary gets its own smoke test, because `bun test` structurally cannot fail on this**
(S18a): every path that broke resolves correctly from a checkout, so 210 passing tests said nothing about
the artefact users install. `packages/bench/smoke/` compiles the CLI, runs it in a fresh temp directory with
no `node_modules` and no workspace above it, and asserts the sequence a new person actually performs —
`init` writes the scaffold *and* `.mcp.json`, `build` produces a site, `serve` answers `initialize`. It asserts
**exit codes as well as output**, because an installer, a CI job and a `&&` chain all act on the code and
nothing else: a `build` that prints a stack trace and exits 0 is a worse defect than one that fails loudly,
and only a test that runs the binary can tell the two apart.

48. **A gate measures the artefact, or it does not measure anything** (S18a): two of this session's three
findings are the same fault wearing different clothes. The spec assets were asserted to work in a binary by
a comment written in S3 and never run. The 50 ms cold start is real on `bun packages/mcp/src/server.ts` and
3× over on the binary that answers the same request. Both stayed invisible for the same reason — every test
and every bench lane runs from a checkout, where the paths resolve and the lazy imports stay lazy. So the
rule, and it applies to D2 as much as D5: **a budget in §1 is measured on the thing a user installs, or the
budget is moved to report-only until it can be.** `packages/bench/smoke/` is where that happens for the
binary; the sequence it drives is a first run, not a unit test, because the failures being hunted are the
ones that only exist once the code leaves the repo it was written in.


49. **The lazy imports were flattened, not defeated — so the fix is `--splitting`, and the gate moves onto the
binary** (S18c): D2 says `initialize` in ≤ 50 ms, and it had been measured since S4 by spawning
`bun packages/mcp/src/server.ts`, which is a command no user runs. The artefact answered the same request in
**224 ms**. S18a's diagnosis named `--compile` — "it evaluates the bundled graph at startup, so decision 11's
own JSON-RPC layer and §3.4's lazy `import()` chain buy nothing there" — and that was wrong in the way that
matters, because it implied the two things holding the budget up had to be replaced. They did not. The bundle
keeps every `import()` lazy (318 deferred module initialisers in it); what it does not keep is the **file
boundary**, and JSC parses all 5.5 MB before `main()` runs. Two measurements separate parse from evaluation
and neither needs a profiler: the same bundle run by plain `bun` is just as slow as the binary (133 ms vs
34 ms from source, so `--compile` is not the cause), and the pre-fix binary took **277 ms to print its own
usage line** — a command that does no work at all, costing more than one that opens a transport. `--splitting`
gives each `import()` its own chunk in `$bunfs`, parsed when it is reached: **224 → 60 ms median, interleaved,
on a box at load 14.7 where the source lane itself read 69.9 and a hello-world binary read 11.9.** The binary
and the dev loop are now the same speed, which is the outcome to hold onto — the artefact is no longer a
different product.

`--bytecode` is the obvious companion and cannot be used: it forces `format: "cjs"` and Bun refuses
`--splitting` outside ESM. It is also the smaller lever, since `--splitting` has already reduced the entry
chunk to 7.6 KB. Both flags were verified on the 1.3.14 lane as well as 1.4.0.

Two consequences are structural rather than numeric. The recipe moved to `packages/bench/src/compile.ts` so
the benchmark that gates the number and the smoke test that runs the artefact compile the *same* binary — two
recipes is how a gate goes green on something a release does not ship. And the two lanes are sampled in the
**same interleaved rounds**, because this project is developed on a box that sits at load 10–15 on four cores:
an absolute millisecond figure from one session is worth little, and the delta between two rows measured
seconds apart is worth a lot. The smoke test asserts the shape rather than a deadline — *printing the usage
line must cost less than starting a server* — which is load-insensitive, and false the moment `--splitting`
is dropped.



50. **The Desk renders its own document, and approval stays on the review page** (S18b′): two shape
decisions fell out of building decision 44 rather than arguing it, and both are load-bearing.

**Its own document.** The review page wears the theme's `page` layout, correctly — it is showing a
draft in the context it will publish into. The Desk is a dashboard, and a dashboard wearing the public
site's nav and footer misrepresents where you are. Owning `<head>` is also what makes decision 45's
`<meta http-equiv="refresh">` valid markup instead of an injection into `<body>`, and it lets the Desk
carry its own small stylesheet: a theme author cannot break the operator's page, and the operator's
page cannot drift when a theme is swapped mid-session. It links the same `/assets/theme.css`, so it
inherits type and colour without inheriting chrome. **The cost of bringing your own colours is owing
both schemes** — the first version used light-mode literals for two labels and opened the new bench
lane at 2 a11y violations, because headless Chrome reports `prefers-color-scheme: dark` and
`editorial`'s background is #12110f there. Every Desk colour is now a token with a `light-dark()` pair
as its fallback, and the Desk paints its own `background` and `color` rather than assuming a theme did.

**Approval stays on the review page.** A Desk row links to `/_snypd/review/{type}/{slug}`; it carries
no approve button of its own, and the Desk carries no `<form>` at all. An approval is bound to the
bytes a human read — `contentHash` of the source the review page rendered, which is what makes "edit
after approving and the approval no longer applies" true — and a button beside a one-line summary
would quietly sever that: the reviewer would be signing a title. The Desk answers *what needs me*; the
review page is where you find out *what you are agreeing to*. Keeping those on two pages is the
difference between a queue and a rubber stamp, and it is also the wall decision 44 needs, because the
first authoring affordance anyone proposes is a button on the dashboard.

**And a corollary to decision 48.** That decision said a gate measures the artefact or it measures
nothing. This session adds: *a surface no suite visits has no gates at all, however green the suite
next door is.* `page.a11y.violations` has read 0 since S13 and the review page has shipped since S11
with a `<pre>` a keyboard cannot reach — not a regression the gate missed, a route the gate never
loaded. Hence `desk.*` as its own namespace over its own routes rather than more routes folded into
`page.*`: a lane that covers a second surface under the first one's name is how a number stops meaning
what its history says it means.


51. **A fifth verb, because `serve` has two audiences and only one of them is a person** (S18e; written for S18d, moved by the docs/08 audit): docs/00 §1
says three verbs and 06 §1 says four; this makes five, six counting `config` and `lint`, which have been
debugging aids since S5. The principle that is load-bearing is *MCP is the only way to write*, and `dev`
writes nothing — it serves what a build already produced. This amends the count in both, and nothing else
in either.

The reason is audience, not features. `serve` is spawned by the harness from `.mcp.json` (`site.ts:197`):
no TTY, and stdout carries JSON-RPC, so a human-facing line printed there is a protocol violation and a
browser opened there is a window per session start. `--preview` bolted the second audience onto the first
verb, which is why the front door is invisible — `cli/index.ts:87` prints the S11 review path with
`<type>/<slug>` placeholders and has never named `/_snypd`, three sessions after the Desk became a page.
`snypd dev` gives the person their own verb with their own defaults: bind, open, watch, print. `serve
--preview` stays as an alias, and the strings that name it (`tools.ts:56` and the publish refusal hints)
move with it.

**The transport question, decided rather than left open.** A single `snypd start` that both speaks MCP and
owns the browser requires HTTP transport: stdio means the *client* spawns the server and owns its pipes, so
a server started in a terminal cannot be attached to. Three costs keep it in v0.3 where 06 already had it.
It needs a localhost auth story in v0.1 — a token file, `127.0.0.1` binding, Origin checks — because
otherwise any process on the box, including an npm postinstall, can publish to your site, and any page you
visit can try DNS rebinding. Harness support for URL-registered servers is less uniform than for spawned
ones. And the failure mode is worse in the case that matters: a spawned server always works because starting
it is not the human's job, while a URL registration for a server nobody remembered to start leaves the agent
with no CMS at all.

**Two processes are not a compromise, because of principle 3.** Files are truth, so the working tree already
*is* the shared state: the agent writes, the watcher sees. The single fact that is not a file is "is a
harness connected", today a function handed in-process (`preview.ts` `opts.activity`, `tools.ts:115-120`).
It becomes `.snypd/activity.json`, re-read per request and never cached, for exactly the reason
`approvals.json` is — two processes over one store make a cache wrong the first time the other one writes.
That file is the entire seam, and it is designed to be **deleted**: the day `dev` also serves an MCP
endpoint, one process holds both again and the heartbeat goes away. Build toward a future that arrives as a
deletion rather than a rewrite.

**Ownership inverts, and that is the point.** The preview stops belonging to the agent's session and starts
belonging to the person: it exists before any tool call, survives the harness restarting, and is already
open when the post lands. `render_preview` probes `.snypd/dev.json` and returns that URL instead of binding
a second server — which also closes a live defect, since both paths default to 4321 (`preview.ts`
`opts.port ?? 4321`) with no fallback, so a human running `snypd serve --preview` while an agent calls
`render_preview` gets `EADDRINUSE`. With no `dev` running the current session-scoped behaviour is unchanged,
so the kill test, which drives `preview()` as a library, does not notice any of this.

**Landed S18e, with two amendments the building found.** *The probe, not the record.* "Probes
`.snypd/dev.json`" turned out to be the wrong verb: a file says a server *was* there, and handing an
agent a URL served by whatever else now holds that port is worse than binding a second one. `/_snypd/alive`
answers `{snypd, pid, root}` without building anything, and `liveDev` proves the claim — and deletes the
record — before anybody acts on it. *The fallback is still worth having.* Discovery covers the case this
decision described; a bind that scans covers the one it did not, which is a port held by something that is
not snypd at all. An explicit `--port=` still refuses to move, because a person who typed a port has an
opinion about which one and a second address they did not ask for is worse than an error.

**Live reload may not change a published byte.** S11's claim is that the preview is the same build that
publishes, so nothing is injected into the page body: a `Refresh` response header does the reloading and the
preview-only link strip to the Desk is added in the response path, with a test asserting that every
`.snypd/preview/**/*.html` equals what `build()` writes to `dist/`. Preview-only behaviour lives in the
response, never in the bytes.

52. **Onboarding state is derived from disk, never stored** (S18d/S18f — **landed S18f**, with the checklist, the three surface labels, the verbatim registration block, the `<details>` and the rendered empty state; the sixth fact reads `.snypd/activity.json` rather than a process's memory, per decision 70): the first-run Desk is a checklist of six
facts — is this a git repo (`isRepoRoot`), does `snypd.yaml` load (`loadConfig().ok`), does `.mcp.json` name
snypd, has a harness ever called (the heartbeat), is there one item (the index), and is `site.url` still a
localhost placeholder. None of it is written down. A progress file is wrong the first time somebody clones
the repo, deletes the only post, or starts over, and it would be a second source of truth in a project whose
third principle is that there is one. The same six facts are what `site` › doctor answers, so there is one
implementation and not two.

Two details carry more weight than they look. **Every row is labelled *type this* or *say this to your
agent*** — half of onboarding is a shell command and half is a sentence to a harness, and people stall
precisely where nothing says which of the two they are looking at. And there is **no dismiss button and no
stored flag**: when the six are true the checklist is not rendered, and what remains is the ordinary Desk.
The "what is MCP" copy sits inline in `<details>`, which is progressive disclosure at zero JS, so it costs
the reader who already knows nothing and `desk.js.kb` stays 0.

**The empty state is rendered, not scaffolded.** `initSite` writes a config and empty directories and no
content (`site.ts:216-252`), so the first visual today is an empty index — the weakest possible first
impression of a themed CMS. The fix is not a welcome post: a file every new site must delete is a file that
ships to production when somebody forgets, and WordPress's "Hello world!" is the demonstration rather than
the counterexample. Instead the dev server synthesises the index route while the site has zero items — the
theme rendering the vocabulary, marked as visible only to you and gone on the first real post — and a test
asserts `build()` never emits it. Nothing exists that must be deleted, and nothing can leak into `dist/`.

53. **`sites/` holds working copies, and this repo tracks none of them** (S18g): S1 listed
`sites/snypd.rocks/` inside the monorepo and S19a pushes snypd.rocks to its own GitHub repo wired to
Cloudflare Pages. Both cannot be true — a site the host builds from git is its own repo. Resolved in favour
of S19a: `sites/` is git-ignored wholesale, every directory in it is its own repo, and snypd.rocks is
*cloned* into it. Beside the code for dogfooding, tracked only by its own remote. One rule, no exceptions.

In-repo rather than `/tmp` for a specific reason: `.mcp.json` written from a checkout names `bun <entry>`
(`site.ts` `mcpEntry`), so a scratch site is wired to the working tree — change the code, restart the
harness, the change is live. Not `corpora/`, because those are bench inputs and must stay deterministic; a
hand-played site among them is how a number stops meaning what its history says (decision 48). And this does
not replace `packages/bench/smoke/`: a site under `sites/` resolves `@snypd/*` through the workspace
`node_modules` and a real user's site does not, so `sites/` dogfoods the *experience* while the smoke test
dogfoods the *distribution*. Collapsing that distinction is how S18a's bug survived all the way to the
binary. `bun run scratch` creates one and starts `dev` — zero to first visual in one command, and since it
is the same path a new user walks, using it is testing it.


**Decisions 51–53, as amended by the docs/08 audit (29 Aug).** Three corrections, made because that
document declared *agent-first* and then designed every deliverable for a person at a screen.

*51* stands as a verb and as a defect fix — the EADDRINUSE collision it predicted is live, and a preview
that outlives the agent's session is worth having. What does not stand is the reasoning that made it the
**front door**: the argument was that a browser tab is the only surface surviving the harness restart,
which is true of a human and false of an agent, whose continuous surface is the repo. Files are truth, so
the thing that crosses the restart is a disk read, not a tab. `dev` therefore serves the terminal-first
arrival and the review moment, and the first run does not depend on it.

*52* is right and generalises further than it claimed: the same derived facts are what `site` › doctor
answers, and doctor — not the Desk — is the surface the agent-first user actually has. docs/08 decision 64
makes that the rule in both directions: no fact appears on the Desk that doctor cannot answer.

*53* is unchanged.

Decisions 54–65 live in `docs/08-first-run.md`, which owns the first run end to end and overrides this
file where they conflict — as this file overrides `06`.

66. **The published launcher is not a workspace member** (S18d′): the launcher on npm — `@snypd/cli`
since decision 71 — is a 20 KB CommonJS shim that resolves one of five platform packages and
`spawnSync`s the binary inside it — esbuild's shape, and bun's. It lives in `packaging/npm/cli`, *not*
`packages/`, for a reason that is not filing: its
`optionalDependencies` name packages that exist only on the registry, so a workspace member declaring them
would make `bun install` in this repo try to fetch five packages that are not published yet. `packages/*`
is what this repo builds; `packaging/*` is what a release is cut from, and `packaging/npm/build.ts` derives
every artefact of one — five packages, five tarballs and their hashes, the Homebrew formula — from a single
`TARGETS` list and the root version. A sixth platform is one row; a version bump is one field.

The shim is CommonJS with a `node` shebang and no dependencies, because `npx` runs it under Node and `bunx`
under Bun and it has to start under the worse of the two. It uses `spawnSync` with inherited stdio rather
than anything cleverer: `snypd serve` speaks MCP on stdin/stdout, and the one thing a wrapper may not do is
buffer or decode a byte of that. Inherited fds are the child's own — the protocol never enters the wrapper.
The cost is one Node boot (~25–40 ms) in front of every run, which is exactly why decision 67 does not
register that path with the harness when it can name something better.

67. **A committed registration names the most portable command that is demonstrably present** (S18d′,
closes docs/08 §12.8). `.mcp.json` is committed, so it has two readers who want different bytes: the person
who just ran `init`, for whom any working command will do, and the clone on another machine, for whom an
absolute path under someone else's home directory is a guaranteed failure — and the *undiagnosable* kind,
a server that spawned and crashed, which the Desk renders identically to a harness nobody restarted. S18a
wrote `process.execPath` and was right about the hazard it was avoiding (naming a command the harness
cannot spawn fails in a log nobody reads); the fix for that hazard is to **look before naming**, not to
give up on the name. Four branches, in order: `snypd` resolved on `PATH` → `snypd serve`; a binary living
in a `bunx`/`npx` cache → `bunx @snypd/cli serve` / `npx -y @snypd/cli serve`, because that path is collected and
writing it produces a registration with an expiry date; a Bun checkout → `bun <entry> serve`; otherwise the
running binary, S18a's answer, now the fallback. All four are walked against the compiled artefact, because
three of them are unreachable from `bun test` by construction — it runs under Bun and always takes the
checkout branch. `site` › doctor resolves whatever the file names, on `PATH` as well as on disk, and says
so.

68. **The host's build command is an installed, pinned command — never a pipe to a shell** (S18d′). §3b
specified `curl -fsSL https://snypd.rocks/install | sh && snypd build`, which S18d′ refuses on the two
counts docs/08 decision 56 already made about installation generally: it is the weakest trust story
available, and it is unrunnable by an agent without a human approving a pipe to a shell. `init --deploy`
writes `npx -y @snypd/cli@<version> build` instead — attested by provenance, and pinned because a deploy config
is a reproducible-build artefact: an unpinned command means a release of ours rebuilding somebody's live
site without them asking. This is the one place the distribution story is load-bearing rather than
convenient, and `deploy.test.ts` asserts the absence of `curl` and `| sh` as much as the presence of the
command.

69. **The first publish is a release decision, and the session stops at the button** (S18d′). Everything
before it is automated and rehearsed: the workflow builds five platforms, runs `npm publish --dry-run` over
each, and publishes only on a `v*` tag whose version it has checked against `package.json`. The publish
itself needs Sunny, for the reason docs/08 §14 gives — a scoped unpublish window is 72 hours, the name is
claimed permanently, and it cannot be rehearsed on this box. So this row is *done up to the button*, and
`bunx @snypd/cli init` is built and tested rather than true. A session that publishes on its own authority is a
session that made a release decision it was not asked to make.

70. **The heartbeat is a file, and it records two facts rather than one** (S18f). Decision 45 said the
Desk may never touch `initialize`, and the cheapest way to obey it was to keep "is a harness connected"
in a module-scoped object inside `protocol.ts` — the one funnel every message crosses, already on the
cold-start path, no new module. That was right about the cost and wrong about the reader. Since S18e the
preview is normally `snypd dev`, a *different process*, so the page whose one job is to answer *did it
work?* answered **no** through a full MCP session (docs/08 §12.9). It was wrong for every user who had a
preview open, which is every user at step 12.

So the record is `.snypd/activity.json`, and three properties keep it from costing what it fixes.
**It is written by a leaf.** `@snypd/core/heartbeat` imports `node:fs`, `node:path` and one string;
`INDEX_DIR` moved down to `paths.ts` so that stayed true, because the package index would have brought a
YAML parser, Zod and a SQLite driver onto the path D2 budgets at 50 ms. **Nothing is written in the first
quarter second.** The first three designs all wrote inside the window between spawn and the harness
receiving its `initialize` reply — a zero timer at `listen()`, then a lazy module import, then a zero
timer on the first call — and all three cost the compiled binary 5–10 ms of best-case cold start against
a ±2 ms same-binary control. *After the reply is on the wire* was true of the source order and false of
the clock: `output.write` to a pipe buffers, the timer phase reaches the loop first, and a module parse
plus a `writeFileSync` land ahead of the flush being measured. So the first write is scheduled 250 ms
out and later ones are throttled to a second; a harness sends `initialize` immediately, so that record
already carries the first call, and the Desk turns green a quarter of a second after it would have on a
page that refreshes every ten.
**It is atomic or absent**: write-then-rename, since the reader is another process polling on a timer and
a half-written object read at the wrong moment renders as "no harness", which is the exact lie being
fixed.

The second fact is `startedAt`, written when the transport comes up and before any message. That is what
makes docs/08 §10's undiagnosable case diagnosable: **spawned and silent** (we are running and the
harness has never spoken to us — a registration problem, and its own log is where to look) is a different
sentence from **never spawned** (you did not restart), and a dead pid is a third — *it was here and it is
gone*. All three rendered identically as one grey line until this session.

*The defect shipping it found.* `SiteIndex.open` has dropped a `.gitignore` holding `*` into `.snypd/`
since S6, and that — not the root `.gitignore` — is what has kept the disposable directory out of
`git status`. `initSite` writes the root file only when there is not one already, so any repo that
predates snypd never got the `.snypd/` line. The heartbeat writes into that directory *before* any index
opens it, so on such a repo `Repo.useDrafts` began refusing every write with *"1 uncommitted change(s) in
the tree (.snypd/activity.json)"* — a file the user never wrote, which is docs/08 §10's shape again.
`ensureDisposableDir` is now the one implementation and both callers use it.

71. **The launcher is `@snypd/cli`; the command is `snypd`** (S18h). npm refused the bare name, twice and
for two different reasons, and only the second is interesting. The first was a credential: a granular
token can write inside a scope it names and cannot *create* a new top-level package — which is why one
run published all five `@snypd/*` with provenance and 403'd on the sixth, a pair that is its own
diagnosis and needed no probe to confirm. The second survived an all-packages token:

> `E403 … Package name too similar to existing package snyk; try renaming your package to '@snymrova/snypd'`

That is a registry rule. No token, no retry and no version bump reaches past it, it fires only on a real
`PUT` — so `--dry-run` cannot see it, exactly like the token before it — and it is opaque, so a
replacement name cannot be pre-cleared: each candidate costs one attempt. npm's own remedy is a scope,
and we own one.

**What actually changed is one string, and the reason to write this down is how nearly it was more.** The
launcher's `bin` map is `{ "snypd": "bin/snypd.js" }`, so `npm i -g @snypd/cli` still puts `snypd` on
`PATH`; the binary, `snypd.yaml`, `snypd://`, the domain, the verbs, the Homebrew formula and the five
platform packages are all untouched. Only what a person types *before anything is installed* moves — and
that string lives in exactly three places that must agree or the majority path breaks for a stranger and
nobody else: the sentence in `ONE_SENTENCE`, the build command in `deploy.ts`, and the `bunx`/`npx`
branch of decision 67's `.mcp.json`. So it is named once, as `deploy.ts` › `LAUNCHER`, beside `VERSION`
and for the same reason.

One rider in `packaging/npm/build.ts`: the launcher stages at `<out>/npm/launcher`, a directory named for
its *role*. Staged at `npm/@snypd/cli` it would be swept up by the `@snypd/*` glob in `release.yml`, and
that glob is the only thing keeping the binaries published before the launcher that pins them —
`packaging.test.ts` asserts the ordering by reading the loop, and would have gone on passing while the
guarantee quietly left.

**And 0.1.0 is superseded rather than merely old.** The published 0.1.0 binaries have
`npx -y snypd@0.1.0 build` compiled into them, so their `--deploy` writes a host command naming a package
that cannot exist. That is a defect on the registry, not a stale version, which is why S18h ships 0.1.1
rather than moving a tag: `@snypd/cli@0.1.0` was free and taking it would have paired a correct launcher
with five binaries that write a broken build line. Deprecating the 0.1.0 platform packages with a pointer
to 0.1.1 is a one-command follow-up and belongs with whoever holds the token.
