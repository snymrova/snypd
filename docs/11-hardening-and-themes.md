# 11 — Hardening, speed, and the theme ecosystem (Gate E)

**Written 13 September 2026, after the fast-forward.** docs/10 planned the launch; this plans what the
software has to be when strangers arrive at it. It is a shorter document than docs/10 on purpose: the
mechanism is built, and what follows is an audit with addresses, a quality gate, and the order the
remaining work goes in.

Sunny's calls on 13 Sep, all three recorded in §8: **the launch moves to 6 October** (the fallback, taken
deliberately rather than discovered), **a theme may ship a webfont** with a declared budget, and Block 0 —
this session — runs first.

---

## 1. The stake

Every number in docs/05 and every claim in the README is true of a tree that one person has run on one
machine. The launch changes the population: strangers, their content, their agents, their plugins, and
their Bun. The audit in §3 is what changes when *correct for me* has to become *stays correct for them*.

The other half is the shelf. docs/10 §6 says npm is the registry and snypd.rocks lists — but a list of
one theme and a null theme is not an ecosystem, and nothing in the tree can yet tell a stranger whether
the theme they wrote is any good. Ghost's marketplace works because GScan runs before a human looks.
That validator, here, is one command built out of checks that already exist somewhere in the bench.

## 2. Where we stand, 13 September 2026

Three things happened this morning, in this order, and they were all housekeeping that had been owed for
a week:

**`main` is the branch a stranger clones again.** It sat at S18k while nine PRs stacked linearly on top

**v0.1.4 is cut.** 0.1.3 predates P1–P4 and U3, so a host building with it knows nothing about
`plugins:`, `transform`, `emit`, plugin tools or `theme.settings`. The bump is the ten version fields in
lockstep, as in 0.1.2 and 0.1.3; `deploy.VERSION` reads its own `package.json`, so a fresh
`init --deploy=cloudflare` pins 0.1.4 with no second edit.

**The publish failed on the credential, not the code.** Every step before it passed — typecheck, the full
suite, `tag matches package version`, all five platform binaries cross-compiled — and then:

> `npm error code E404` · `404 Not Found - PUT https://registry.npmjs.org/@snypd%2fdarwin-arm64`

A 404 on a `PUT` to a package that demonstrably exists is npm declining to admit the package exists to a
caller that cannot write it — the shape an **expired or revoked token** makes, not a scope problem
(`packaging/README.md` §2 records the 403 that a scope problem makes, and this is not that). Nothing was
published: the loop skips what is already on the registry and stops on the first real failure, so the
registry is untouched at 0.1.3 and the run is re-runnable once the secret is good.

`packaging/README.md` §2 already anticipated the fix: *"Once the packages exist, npm's trusted publishing
can replace the token entirely and the secret can be deleted."* All six packages now exist. The token is
the unblock; trusted publishing is the repair, and it cannot expire again.

**Still owed, and it is Sunny's hand:** the npm credential, and the Cloudflare pin — which lives in the
dashboard and moves to `@snypd/cli@0.1.4` once npm has it. D7 goes green on that one edit, and U2's menus
and P3's `autolink` reach the public page the same minute.

## 4. Speed — profile first, and say which number you are buying

The honest position: **speed is not a user problem.** 100 pages cold is 728 ms here and 224.9 ms in CI
against a 2,000 ms budget; incremental is 17.5 ms; the binary answers `initialize` in 33.7 ms against 50.

What is structurally true is that `build.ts` assembles a `plan[]` of pure, content-keyed items and then
walks it with a `for`, synchronously. The only `Promise.all` in `@snypd/render` is theme module loading.
A sixteen-core machine renders 10,000 pages on one of them, in 21.7 s.

Parallelism is the right *shape* — the items are already pure and keyed, which is the hard part, and
D9's byte-identical assertion is exactly the test that would prove order does not matter. It is not the
right *next thing*, for three reasons: `phases: { config, theme, sync, plan, render }` is already
instrumented and nobody has published the split; `lint.100.cold` at 425 ms against `lint.100` at 18.9 ms
says the cold cost is parsing, which a worker pool re-pays per worker; and workers cost process startup,
which is the one budget an agent actually feels.

**So F1 publishes the profile for 100, 1,000 and 10,000 pages, adds the missing `build.cold.1000` lane —
where most real sites live and no lane covers — and the decision is recorded either way.** "Single-threaded
on purpose, here is the profile" is a perfectly good answer to write down; "we never measured" is not.

> **Outcome, 15 September 2026 (F1).** The 1,000 lane was not missing — CI runs every size and the
> committed record was a `--quick` run from this box, which is the one thing this section got wrong. What
> was missing was the split. `build()` now carries `profile` — the render phase as `parse` (the mdast
> cache: micromark on a miss), `html` (the theme's TSX and `toHtml`), `write`, `weigh` (H2), `index` and
> `stat` — and `bench` publishes it per size, read off the median run, with a report-only
> `build.cold.<n>.parse` row. **From CI, on a four-vCPU runner:**
>
> | | 100 | 1,000 | 10,000 |
> |---|---|---|---|
> | `build.cold` | 318 ms | 2,878 ms | 28,860 ms |
> | an item | 2.57 ms | 2.81 ms | 2.88 ms |
> | parse | 237 · **74 %** | 2,226 · **77 %** | 22,237 · **77 %** |
> | html | 31 · 10 % | 224 · 8 % | 2,425 · 8 % |
> | write | 23 · 7 % | 226 · 8 % | 2,397 · 8 % |
> | weigh | 8 · 3 % | 92 · 3 % | 762 · 3 % |
> | sync + plan + index | 13 | 98 | 996 |
>
> Linear in *n* — 2.6 to 2.9 ms an item from 100 to 10,000 — and the parser is three-quarters of it at
> every size, 2.2 ms a page, which is the S6 finding ("micromark ≈ 450 of 699 ms") holding at two more
> orders of magnitude. **The decision is single-threaded, on purpose (166).** The arithmetic: the CPU a pool
> could split is parse + html, 85 %; four workers take a 1,000-page cold build from 2.9 s to 1.0 s at best,
> and 2.9 s is 14 % of its budget. The build an agent pays is `build.incremental.100` at **12.8 ms**, one
> route rendered, where a pool has nothing to split and a spawn to pay. And S20's lever sits on the same
> 77 %: docs/04 measured `Bun.markdown` at ≈ 45 MB/s against micromark's ≈ 0.4, so a parser ten times
> faster removes ~70 % of the build, where four cores remove 64 % at most and cost a pool. The order is the
> parser first; cores never, until `build.cold.1000` in CI passes half its budget. The worker experiment
> (`_workers.ts`, a pool importing the parser fresh and posting JSON back) was written and not run: this
> box was at load 20 on four cores all session, and a ratio measured there is a ratio of the load.

## 5. Beautiful — what it costs, in order of effect

Two themes, one of them deliberately unstyled. `editorial` is genuinely well made — fluid `clamp()`
scales, a 34 rem measure, `light-dark()` on every colour token, six spacing steps — and it is one look,
tuned for a serif most visitors do not have.

**1 · Type.** `editorial`'s body stack is `'Iowan Old Style', 'Palatino Linotype', Palatino, Charter,
Georgia, ui-serif, serif` with the comment *"a webfont is a network round trip this theme will not
spend."* That refusal was aimed at a 300 KB family and a third-party origin, and neither is the 2026
proposition: one subsetted variable WOFF2 is ~30 KB for a Latin subset, self-hosted (cross-origin font
caching died in 2021, so the shared-cache argument is gone), `font-display: swap`, preloaded, with a
fallback face carrying `size-adjust`, `ascent-override` and `descent-override` matched to it — so the
swap shifts nothing and `page.cls` stays 0 rather than being traded away. **Decision 118 permits it with
a budget lane**, and the claim becomes *zero JS, one font, both declared*, which is stronger than *zero JS
and whatever your OS has*. **Done in B1** (§7b): Source Serif 4, 30.33 KB against a 40 KB lane, `page.cls`
still 0 — and the estimate above was right about the size and wrong about what fits in it, because a
roman, its bold and its italic do not (`editorial`'s `font:` block carries the three measurements).

**2 · Variations** (U6a, already scheduled) are the cheapest breadth available: three complete token sets
per theme, each named and described. Worth pairing with OKLCH and relative colour syntax —
`oklch(from var(--color-accent) calc(l - .08) c h)` derives hover, border and surface from one accent
instead of declaring twelve, so a variation is a few lines and stays perceptually even.

**3 · The Baseline CSS that is free.** `@layer` (finding 5, and an extensibility fix before it is an
aesthetic one); container queries, so an entry card adapts to *its* column rather than the viewport;
`text-wrap: balance` on headings and `pretty` on prose; and `@view-transition`, which gives a static
multi-page site cross-document transitions with **zero JavaScript** and is silently ignored where
unsupported. None of these move `page.js.kb`, which is the point of choosing these five. **Four of the
five are done** — `@layer` in H0, `text-wrap` in `editorial` since S14 and in `technical` from its first
line, `@view-transition` in both in U6b (decision 138: it survives the cascade layer, which `@import`
does not, and that was checked in a browser). Container queries are unclaimed: nothing in either theme
has yet wanted a component that adapts to its column rather than the page, and adding one to say the
word would be the kind of feature docs/07 principle 9 exists to refuse.

**4 · A contrast gate.** With finding 2's validation in place, WCAG ratios can be computed from the token
set at `theme check` time: a theme whose muted-on-background is below 4.5:1 fails before a human looks.
**Done in X1** (§7b), and it is seven pairs rather than one — text, muted and accent against both the page
and a raised block, plus text on an accent fill — measured on every look a theme ships and on every side
of `light-dark()` that look actually renders. The paragraph above was right that the values were enough
and wrong that they were *readable*: `oklch(from var(--color-bg) calc(l + 0.045) c h)` is what a well-made
2026 theme writes, and nothing in this repository could turn it into a number. About a hundred lines of
arithmetic now can (decision 141). The tightest ratio on the shelf today is `technical` › `phosphor`,
muted on a raised block, at **4.97:1** — which is the number the gate exists to have.

`technical` (U6b) should be a different argument rather than a recolour: a denser measure, mono for
headings, tables and code as first-class citizens, a table of contents from the heading tree. Three
themes × three variations is nine looks from one contract, and the gallery is what makes the shelf worth
visiting. **Done in U6b** (§7b), and the paragraph above was right about what to build and wrong about
what it would cost: the contents list was one part and one field short of being buildable from the
contract at all (decisions 135, 136), which is the finding the session existed to produce. Two themes ×
five variations is **five looks**, not nine — `editorial` ships three and `technical` two, which is what
docs/10 §5.2 said and what the gallery will show.

## 6. What is *not* in this plan

Deferred with a reason, so nobody re-proposes them every quarter:

- **Sections and blocks / page building.** Shopify's schema model and WordPress's block themes both solve
  "let a non-technical person compose a page". Composition here is the primitive vocabulary and the
  composer is the agent; adopting either puts a dashboard back in the middle of the product. docs/09 §4.5
  deferred variants and patterns and they stay deferred.
- **Sanitizing content.** See finding 1.
- **Parallel rendering.** F1 said no, with the profile (§4, decision 166): the cold build is parse-bound,
  a worker re-pays the parser's import and the agent's build renders one route, so the number to buy is
  the parser's per-page cost — S20's question — not the core count. Revisit when `build.cold.1000` in
  CI passes half its budget.
- **DTCG import/export and `@snypd/plugin-test`** — both are real ecosystem reach (the W3C Design Tokens
  format reached its first stable version, 2025.10, with Adobe, Figma, Google, Microsoft, Shopify and
  Salesforce behind it, and `theme.yaml › tokens` is already the same idea). Post-launch: X2.
- **Everything in docs/10 §7's "does not block launch" list**, unchanged.

## 8. Decisions

**117. The launch moves to Tuesday 6 October 2026**, 00:01 Pacific — the fallback docs/10 already named,
taken deliberately on 13 Sep rather than discovered on 25 Sep. The date was never announced, so it costs
nothing; decision 93 still holds, and the gate is still the gate. What the extra week buys is sessions
1–9 rather than a smaller Gate D.

**118. A theme may ship one webfont, declared and budgeted.** Self-hosted, subsetted, variable, WOFF2,
with a metric-matched fallback face so the swap shifts nothing. New lane `page.font.kb`: **0 for `base`,
≤ 40 KB for a themed one**, measured on the wire like `page.js.kb`. This reverses `editorial`'s own
comment, which is why it is a numbered decision and not a commit.

**119. The stylesheet is emitted in cascade layers.** `@layer snypd.tokens, snypd.base, snypd.theme,
snypd.site;`, each sheet wrapped as it is concatenated. Before third-party themes exist this is a no-op;
after, it is a breaking change to everyone's CSS. It happens in session 1.

**120. A value may not change the meaning of the sheet.** Token values and settings of kind `color`,
`size` and `font` are validated against a conservative CSS-value grammar; the refusal names the token and
the line, like every other refusal in this codebase.

**121. The 0 KB claim is enforced on the user's own build**, not only on the bench corpus. A build that
emits script beyond what plugins declared fails with the file and the line — the same treatment a plugin
over its client declaration already gets.

**122. Raw HTML in content is `warn` by default.** `content.rawHtml: allow | warn | refuse` in config.
Never silently stripped: the source file *is* the `.md` twin (docs/01 §2), and a renderer that rewrote it
would be decision 102's failure arriving by another door.

**123. `theme check` is the gate for the shelf.** `/themes` and `/plugins` list nothing that does not
pass it. Ghost's marketplace is curated and machine-validated first, which is why its listings mean
something; this is that rule, made once, before the first submission rather than after.

**124. Parallelism is not adopted on assertion.** F1 publishes the phase split first. Either answer gets
written down.

**125. L0 is a session.** A licence file and a merged `main` are launch blockers in a way a third theme is
not, and the work was invisible precisely because no session owned it.

**126. A theme's stylesheet may not `@import`.** An `@import` inside a cascade layer is invalid CSS and
is dropped without a word, so decision 119 would have silently unloaded any sheet that had one. Refused by
name and line at `loadTheme`, which is the treatment every other bad theme file gets — and it is the
honest rule anyway: a theme ships one stylesheet, decision 118's budget counts what that sheet ships, and
an import is the network arriving somewhere nothing measures. `@font-face` inside a layer is valid and
untouched, so B1 is unaffected. X1's `theme check` inherits the rule.

**127. A variation is token values, never declarations.** `variations:` may retune a token the theme declares; it may not add one, change its `kind`, or move `customisable`. An invented token has no description and nothing for `theme` › set_tokens to check against — it is a custom property the theme's own stylesheet never reads. Warned by name and line at `loadConfig`; X1's `theme check` is where the same finding stops a theme reaching the shelf. This is the line between a variation and a child theme, and it is what makes "switching changes exactly the tokens it names" assertable.

**128. `variations:` does not merge into the config, and `theme.variation` is the answer.** The rule `settings:` already has (decision 116), one step further on: a site that could write `theme.variations` in `snypd.yaml` would be writing a look nothing could ever apply, because the site layer merges at step 4 and the chosen variation's tokens land at step 2.5. Better to not have the key than to have to warn about it.

**129. `snypd://theme` carries the variation names; `snypd://theme/variations` carries what they are.** The bargain the palette has had since S16, applied to the same read. What each look *is* costs a sentence each, and a sentence per variation on the resource every session reads is a tax on the sessions that never restyle — it took `tokens.learn.editorial` to 4836 against a CI line of 4800. It is also its own resource rather than a block in `snypd://theme/tokens`, because two YAML maps at the same indent in one resource is a resource that gets misread, and this one was, by the kill test, within the hour.

**130. `theme.variation` is cleared by a theme switch.** A variation is a name in one theme's vocabulary. Carrying `ink` across to a theme that never heard of it is how a site acquires a stranded value that warns on every load, so `theme` › set drops it unless the same call names a new one — and when a call names both, the pair is checked against the theme being switched *to* before either is written.

**131. `font:` is a declaration, so it does not merge into the config.** The third key of `theme.yaml` to be read and dropped rather than merged, after `settings:` (116) and `variations:` (128), and the rule is the same one: `theme.*` is what a *site* answered, and there is no question here for it to answer — a webfont is a file in the theme's own directory at a size the theme claims, and a site cannot move either. Left in, it put `font: <theme editorial default — editorial/theme.yaml:34>` on `snypd://config` and 14 tokens on `tokens.learn.editorial`, which is how it was found. `theme.font` written in `snypd.yaml` is now a warning naming the line, and so is `theme.variations` — the loose end decision 128 left, closed in the session that would otherwise have added a second one.

**132. The font budget is the theme's number, and `page.font.kb` is `exact`.** A site affords its plugins a script budget because it chose the plugins (84); it affords its theme nothing, because the theme *is* what it chose — so the lane's budget is `font.kb` from `theme.yaml`, capped at 40, and 0 for a theme that ships none. It passes CI at `≤ budget` and not at 80 % of it, for the reason `Metric.exact` exists (S19c): `CI_FACTOR` is headroom for a clock, a file is 31,056 bytes on every machine that ever reads it, and 80 % of a declared 31 KB is 24.8 KB — a budget nobody wrote down. The slack that is real is already in the declaration, which is the round number above the file.

**133. The install gets a lane, and only the part this repository owns gets a budget.** `install.download.mb` and `install.binary.mb` are report-only and are meant to stay that way: 94 % of both is Bun's runtime, and a gate that fails on somebody else's release is a gate people learn to re-run until it passes. The budgeted row is `install.code.mb` — the release binary minus a one-line program through the same `compile()`, so the runtime cancels on both sides and what is left is every dependency, every bundled theme and the spec: **5.14 MB against 8**. The floor is compiled on the spot rather than remembered, because a constant there would be a claim about a Bun version and the subtraction is only honest if both numbers come from the same compiler on the same afternoon. This is decision 54's rule pointed at the one surface it had never been pointed at: a thing no suite visits has no gates, and until now the thing 100 % of users wait for was that thing.

**134. A generated workflow installs once.** Three `npx -y` lines were three tree verifications of the same pinned package, at 2.2 s each — pinning buys reproducibility and not speed, which was measured rather than assumed — on top of a 37 MB download nothing was keeping between runs. One `npm install -g @snypd/cli@<version>`, three bare `snypd` calls, and `~/.npm` cached on the version the install is pinned to: a content repo has no lockfile, so the pin is the only honest cache key there is. The test asserts the *shape* and not the seconds — one registry step, no `npx` in any `run:` line — because the regression this guards against is a fourth verb added later as another `npx -y`, with the install silently paid again.

**135. The post layout has a contents slot, and `base` fills it with nothing.** `technical` wanted a table of contents, and the two ways to get one without this were both wrong: fork `base`'s post layout, which D8 forbids because a copied markup contract drifts the first time the original changes, or give every theme a contents list whether it asked for one or not. So `parts:` gains a fifth name — `toc` — the post layout renders it between the byline and the body, and `base`'s version returns an empty fragment. A theme that says nothing about it emits the bytes it emitted before the part existed, which is not an argument but a measurement: the whole of `corpora/theme` under `editorial` is byte-identical against HEAD except `assets/theme.css`, and that moved for `@view-transition`. The general rule this sets: **a slot a theme may want is a part with an empty default, never a layout fork and never a conditional in `base`.**

**136. The heading tree comes out of the render that issued the ids, and it is the document's own headings.** A toc built from a second pass over the markdown is a toc whose anchors can be wrong — the ids are de-duplicated as they are handed out, so only the renderer knows that the second "Notes" is `notes-1`. `toHtml` takes an out-parameter and fills it; `renderDoc` returns it; `Page.headings` carries it. It collects **direct children of the root only**, which is a filter and was found by looking: an `faq`'s `###` questions are rendered by the same recursion with the same options and get ids exactly as a section heading does — correctly, because they are linkable — and the first contents list this session built named all of them, describing the page's markup instead of its argument. They keep their ids and stay out of the array.

**137. A theme that declares no `font:` is budgeted at nothing, and `technical` is that theme.** Decision 132 gave the lane a theme's own number; this is the other half of it being true, and the reason `technical` ships no face is not thrift. The face that carries a monospace-led theme is the monospace, and monospace is the one category where the system stack is already excellent on every platform — SF Mono, Cascadia, JetBrains Mono, Consolas, DejaVu. Thirty kilobytes to replace a good face with a different good face is thirty kilobytes for a preference. Measured: `tech.font.kb` **0 / 0**, no `@font-face`, no preload, no `assets/fonts/` in `dist/`, and `tech.bytes.kb` **32.19** against `page.bytes.kb` **60.76** — the difference is the font, and it is the whole difference.

**138. `@view-transition` survives a cascade layer, and that was measured rather than assumed.** `@import` inside `@layer` is invalid and is dropped *silently* (decision 126), which made this the obvious next worry for a declaration `loadTheme` wraps in `@layer snypd.theme.<name>` before anybody sees it. It is not the same: it parses as a `CSSViewTransitionRule` inside both `@layer` and `@media`, and a real cross-document navigation between two layered pages fires `pagereveal` carrying a `viewTransition` — checked in Chrome, on two pages served over HTTP, because `document.styleSheets` proving a rule parsed is not the same claim as a browser honouring it. Both themes get it and both get `navigation: none` under `prefers-reduced-motion`. Sixty-nine bytes on `editorial`'s stylesheet, zero JavaScript, and nothing at all on a browser that has never heard of it.

**139. Two verbs, and neither of them is a noun.** X1's spelling is `snypd new theme|plugin` and `snypd check theme|plugin`, not `snypd theme check`. A noun used as a verb promises a family — `theme set`, `theme list`, `theme install` — and that family exists, over MCP, and is never coming to the CLI: writing is over MCP and only over MCP (decision 51, docs/08 §2), and a second front door for it is the thing this product has refused since S4. What a terminal is for is the one artefact that is *not* content. A theme author is a person with an editor open, and two verbs — make one, judge one — is the whole of what they do here. `theme` › scaffold keeps its MCP door and now calls the same function, so there is one starter file rather than two that drift.

**140. `skip` is a status, it is printed, and it is never a pass.** A checker that cannot reach an answer has to say so out loud. `base` declares no colours, so the contrast rules over it report *not checked* rather than passing; a value in a colour space this build does not implement does the same. The tally line counts skips separately for the same reason. A badge awarded by a parser that gave up is worse than no badge, because the shelf's whole claim (123) is that a listing means something.

**141. The contrast gate is arithmetic, and the subset it implements is written down.** The honest way to resolve `light-dark(oklch(from var(--color-bg) calc(l + 0.045) c h), …)` is to ask a browser, and the bench already drives one — but `snypd check theme` is typed on machines with no display, and a check that needs Chromium is a check nobody runs. So OKLCH/OKLab ↔ sRGB, `light-dark()`, `var()`, `color-mix()`, relative colour and a small `calc()` live in `packages/core/src/color.ts`, tested against values fixed from outside it (white on black is 21:1 by definition; `oklch(1 0 0)` is white by definition). Out-of-gamut colours are clamped rather than gamut-mapped, which is the conservative direction — it never reports a colour as further from its background than it is. Everything outside the subset is decision 140's business.

**142. `check theme` judges the theme, not the site it was run from.** A token the site has moved off its default is read back at the theme's default before any rule sees it, and a diagnostic attributed to `snypd.yaml` is not the theme's finding. Otherwise the same theme passes from one directory and fails from another, which would make the shelf's verdict a property of whoever submitted it. The corollary is that a root with no `snypd.yaml` gets the smallest site that loads, in a temp directory, with the real root as a search path — forced by a bug this verb found on its first run: `loadConfig` validates the whole config, a missing `site.name` fails that validation, and `config` then falls back to the spec's defaults with the theme layer simply absent. Nothing threw. Every variation reported the same tokens, and `phosphor` was measured in a light mode it does not have.

**143. A scaffold's own sentence fails the gate.** `personality:` and `description:` are what a listing prints and what an agent picks on, so the scaffold has to write *something* there — an empty key teaches nothing. But a shelf full of "Describe how this theme reads" is a shelf that has stopped meaning anything. The two strings are declared once, in `scaffold.ts`, and `check` compares against them: the only place in this product where *unchanged since the scaffold* is itself the finding. A freshly scaffolded theme therefore fails exactly one rule, and the rule names the sentence its author has to write.

**144. A theme scaffolded over `base` declares its own palette, because `base` declares none.** Found by running the two new verbs back to back, which is the loop they exist to close. The starter stylesheet has said `background: var(--color-bg)` since U1 and `base` has never declared `color.bg` — so a theme made this way came out referencing eight custom properties that resolve to nothing, and rendered unstyled. The comment above the stylesheet even listed a palette: the *active* theme's, which the new theme does not extend and cannot see. The scaffold now writes twelve declared, described, `customisable` tokens when the parent declares none, and their values clear 4.5:1 on all seven pairs in both modes — asserted by the checker shipped beside them, because a scaffold that fails its own gate is a scaffold nobody should start from.

**145. There will never be a visual designer, a dashboard, or a WYSIWYG.** Super is building one, and says why: *"those without coding knowledge struggle to make their site look how they want."* That is a true problem for their user and not one ours has — ours arrives with an agent that writes CSS, and `snypd new theme` → `snypd check theme` already closes the loop with real WCAG numbers rather than a preview. Building one would contradict principle 1 outright (*if it isn't a resource, tool or prompt, it doesn't exist*) and would solve a problem we do not have, at the cost of the only thing that makes the product coherent. This is recorded as a decision and not a preference because it is the most likely piece of well-meant competitive advice we will receive, and the next person to propose it is owed an argument rather than a shrug. Sunny's call, 13 Sep 2026, on docs/13 §2 Q4.

**146. The tagline is reordered, not renamed.** *"Publish a website from the harness you already have open"* leads; *"Your CMS is wherever your agent is"* becomes the strapline; *"A CMS your agent can actually use — markdown in your repo, static HTML out, zero JS"* is the sub-paragraph. All three sentences are already in docs/00 §One paragraph and all three are already true, so nothing here is a claim that has to be earned — the only change is which one is set largest. The current line names a *location*, which is a good second sentence and a weak first one: it presumes the reader already accepts that a CMS has a location worth arguing about, and a launch visitor gives that premise about four seconds. Decided 13 Sep on docs/13 §2 Q1 (candidate C), ahead of its session-12 deadline, because L1 sets the hero and re-cutting at L2 costs screenshots. **The edit itself rides L2** (docs/13 §3.1): README and the snypd.rocks hero, one ordering change in each.

**147. Script is weighed, never stripped.** docs/11 §3 already ruled out sanitising (the source is the twin, docs/01 §2; decision 102), and H2 makes the alternative concrete: the build scans the page it just wrote, sums the script on it against `bench.budgets.jsKb`, and refuses the whole build with one message naming every page over — page, line, source, bytes. The number is deliberately the one P2 already had, so the site states what it affords in one place and there are exactly three readers of it: what a plugin *declared* (`loadPlugin`), what the build *wrote* (`assertClientBudget`), what the browser *fetched* (`page.js.kb`). A site-local `src` is weighed by the file the build wrote; a data block (`application/ld+json`, any non-JavaScript `type`) is not script, by the browser's own test. The check runs inside the index transaction so a refusal leaves no route row claiming bytes nothing approved. *(Mechanism superseded in H3, decision 152: rolling the row back was the hole, and an open row is the fix.)*

**148. A declaration may stand in for bytes only for script its own plugin rendered.** A remote script cannot be weighed before it runs. The first rule — unweighable is over every budget — refused `analytics`, which is the plugin decision 84 was written for, so the rule is now: `slot()` records the signature of each script site a plugin's slot rendered, and when a page carries a remote script with that plugin's signature, the plugin is charged the larger of the bytes the build could weigh and its `client:` declaration. Attribution is by *who rendered it*, not by host: a host allow list would pass the same `<script src>` pasted into a post, which is finding 1 with extra steps. A plugin that declared nothing has nothing to stand in; a remote script from a content file, a layout or an agent has no plugin and no declaration, and is over any budget, however large.

**149. Lint rule 13 fires on script, not on raw HTML.** Raw HTML is correct CommonMark and the reason an iframe embed, a `<details>` or a `<video>` works; a rule against it would be noise on every legitimate post and would teach authors to ignore rule numbers. `inline-script` is an **error** because it is not advice — it reports the thing the build will refuse, on the source line, earlier. Code fences and inline code are not raw HTML, so a post *about* script stays writable.


**150. A stat taken too close to its mtime vouches for nothing.** The index keeps a file's row when mtime and size are unchanged, except when the mtime is within `RACY_MS` (2 s) of the start of the last sync; such a file is hashed again, and on every sync until one starts comfortably after it. Two seconds is FAT's granularity, the coarsest a site is likely to live on; ext4's kernel tick and HFS+'s second are inside it. One timestamp in `meta` is enough because every row the check distrusts is rewritten by the re-hash with the stat of the sync that distrusted it, and the sync now reads its rows inside its own immediate transaction, so two processes cannot interleave a stale read with a fresh timestamp. The cost is a hash of the file being edited, which an edit that changed its length paid already. Media keys stay size + mtime (the trade build.ts states beside them): replacing an image with a same-size one inside a tick recopies nothing, and H4's property is where that gets decided rather than assumed.

**151. The index is WAL, with a 5 s busy timeout and immediate transactions.** `dev`, `serve`, `build` and an MCP session share one `.snypd/index.sqlite`, and a rollback journal with no timeout turned any overlap into `SQLITE_BUSY` inside an agent's turn. WAL lets readers pass the writer; the timeout queues writers; `BEGIN IMMEDIATE` is what lets a writer queue at all, because a deferred transaction that has read cannot be granted the lock once another connection has committed, and fails whatever the timeout says. `synchronous = OFF` stays — the index is disposable (docs/07 decision 13) — and is set **before** the journal mode, which is the difference between 0.5 ms and 100–200 ms on a new file. The `-wal` and `-shm` files live in the self-ignoring `.snypd/` and are removed on the last close. Deleting `index.sqlite` alone while a `-wal` survives a crash is the one way to feed SQLite a journal from another database; the recovery advice was and remains *delete `.snypd/`*.

**152. A build is a generation: open, render, close.** Before any output is written, every route the build will write gets the key `open:<generation>` and the union of its old and new outputs, in one committed transaction. The render then runs with no transaction and no lock. The close writes the real keys and drops vanished routes. An open key equals no planned key, so whatever stops a build — a kill, a crash, a throw, a client-budget refusal — leaves rows the next build re-renders, and `BuildResult.recovered` counts them so `snypd build` can say so. This replaces the single render transaction, which made the index atomic and `dist/` not, and held the write lock for the whole render; it also supersedes decision 147's last sentence, since rolling a refused page's row back to its previous key is exactly what let a revert serve the refused bytes. The union of outputs is what lets the next build still delete a file the dead build had moved away from. Concurrent builds into one `dist/` are not made correct by this and are not claimed to be — that is H4's property under concurrency, not an example here.

**153. A property is a test that names its generator and its seed.** `packages/bench/props/` is where the six live, each over a generator that produces *data* — a site, a document, an edit, a message — so a counterexample is a printable value fast-check shrinks, not a directory somebody reconstructs. Two knobs and no more: `SNYPD_PROPS_SEED` (fixed at 20260914 in `bun test`, the run id in the `properties` lane, printed first either way) and `SNYPD_PROPS_RUNS` (a multiplier; ×1 in the suite, ×10 in the lane). Every counterexample a property has found is written into `props/corpus.ts` and handed back as an `examples:` entry, so a bug found on one seed is a bug checked on every seed after. The one exception E7 keeps: the index remembers a slug change (`moves`) and a menu `ref` written as a route follows it, which a cold build cannot know — by design (docs/09 U2, lint rule 10), so the generator writes `ref`s as `type/slug` and this decision says why.

**154. An author page's key holds the posts it lists.** The page is a list as much as a page (H1): its entries are every published post by that author, and until H4 its route key held the author's own file and nothing else, so trashing, retitling or adding a post left the author's page as it was until the author's file changed. The first property found it in its first run. The list key already used for the index and the term pages is used here too.

**155. A `url` or `image` prop with a scheme that executes is dropped, not passed.** `checkProp` refused `javascript:` for a `url` prop as *not a URL* and handed the raw value to the theme anyway, and `base`'s `chart` wrote it into `href`. Rule 12 and decision 126 already drop such a value from a markdown link; the same rule now runs on every `url` and `image` prop, the value is `undefined` to the component, and the diagnostic names the scheme. The build's budget (E6) refused such a page before this — this stops a theme being the last thing between a prop lint refused and the page.

**156. A tag that opens and never closes is a script site.** `scriptSites` on the fragment `<script` (no `>`) found nothing, so lint passed it; on the page, the layout's own markup supplied the `>` — `<script\n</article>` is an open tag with a strange attribute — and the build refused what lint had passed. The browser agrees with the build: everything after it is script text until a `</script>` nobody wrote. The detector now reads a dangling tag to the end of its text as the tag it is.

**157. `readFrontmatter` uses the parser's fences.** The index's fast path (no markdown parse) took `\n---` anywhere as the close and refused an opening fence with a trailing blank; micromark closes on a line that is exactly `---` (blanks allowed) and opens on one. So `----` was a fence to the index and a thematic break to the renderer — a post published in the index whose page rendered its frontmatter as body. The two read the same fences now, and property 4 keeps them agreeing.

**158. A media file written inside the racy window is copied again.** Decision 150 left media keys at size + mtime and deferred the same-size-same-tick case to this property; the property found it in one probe: the pages re-rendered (the sizes come from the source) and `dist/media/` kept the old bytes. The rule is the index's own (decision 150) applied to copies: a media file whose mtime is within `RACY_MS` of the sync's start gets a key that includes the sync's timestamp, so it is copied — not hashed, copied, which is cheaper than a hash and only ever paid for the file being replaced right now. `SyncResult.at` is the clock it reads.

**159. A message is read before it is answered, and a broken one is answered whatever its id.** JSON-RPC 2.0 §4–5. A request is an object with `jsonrpc: "2.0"`, a string `method` and an id that is a string, a number or null; without an id it is a notification and earns no reply — *if it is otherwise well formed*. `dispatch` decided "notification" from the absence of an id before it had looked at anything else, so `"a string"` on a line was dropped in silence, `null` threw inside the handler, an object id was echoed back as an object, and `notifications/cancelled` sent *with* an id (a request to a method this server has not got) was ignored rather than refused. Now: an invalid message gets Invalid Request with the id it carried when one could be read and `null` otherwise; a request to an unknown method gets Method not found even when the method's name says "notification"; only a valid notification gets nothing. Found by the two RPC properties across two seeds.

**160. `base` ships one stylesheet, and it is behaviour, not looks.** `base` had no CSS while its markup did nothing a browser needed telling about. Since U7 the markup carries a `popover` menu, a `<dialog>` lightbox, a `<details>` accordion and a hidden footnote card, and each arrives with user-agent styling that would otherwise be every theme's problem before its menu stopped being a fixed grey box: a `<ul popover>` is `display: none` until opened, everywhere, and `position: fixed` and bordered when it is. So `themes/base/theme.css` is the user-agent sheet for snypd's markup — display, position, a reset, the 34 rem breakpoint at which a menu is a row — in the `snypd.base` layer under every theme's own, with no colour that is not a system colour, no type, no token read. A theme overrides any line of it with a plain selector; the phone sheet's *layout* is `!important` on purpose, because a lower layer's important declaration is exactly the tool for "whatever `nav ul { display: flex }` a theme wrote for the desktop, the closed menu on a phone is hidden and the open one is a sheet". A theme that wants a different phone menu overrides the header part, which is what parts are for.

**161. The tier rule, and `check theme` enforces it.** A CSS feature is Baseline and may be used anywhere, including for something the reader needs; or it is two engines of three and goes under `@supports`, never for anything the reader needs to reach content — the fallback must be the page as it is; or it is one engine and goes under `@supports` only where the fallback is *nothing happens*. `GUARDED_CSS` in `render/src/check.ts` is the second and third kinds as data — scroll-driven animations, CSS carousels, `text-box-trim`, `scroll-target-group`, `scroll-state()`, `interpolate-size`, `sibling-index()`, `if()`, `@function`, `corner-shape` — each with the `@supports` test a theme would write, revised when Baseline moves; `css.enhancement-guarded` names every use outside a guard with its line, and warns rather than fails, because whether the fallback is "today's page" or "the menu is gone" is the thing a machine cannot see and an author has to look at. An unsupported *value* (`text-wrap: pretty`) is not on the list: a browser drops the declaration and the page is the page it was.

**162. A footnote's definition is emitted twice, and the second copy is `hidden`.** The renderer holds every definition, so the mark gets `<small class="snypd-fn-card" role="note" hidden>` beside it with the definition inline, `anchor-name` on the mark and `position-anchor` on the card in `style=""` attributes — CSS in an attribute is not script, and rule 13 does not see it. Only a definition made of paragraphs is inlined: a list or a code block inside a `<p>` would close the paragraph, and the card is a phrase or nothing. The `<section class="footnotes">` stays, unchanged — the printable, linkable version, and the one every browser had. `base`'s sheet shows the card on hover and focus, anchored above the mark and flipped below at the top of a page, where a pointer can hover; `editorial` makes it a Tufte sidenote in the margin at 72 rem and above — a float pushed out of the column by a negative margin, sized to what the margin allows so `broadsheet`'s wider measure still gets one — and hides the list at the end while the notes are beside the text. A touch screen with no hover gets the link to the end.

**163. A container's sections are the renderer's.** `PrimitiveProps.sections()` hands a primitive its body split at the body's shallowest headings — each heading's inner html, the id the renderer issued for it, and everything up to the next — as a thunk over the *same* render `body` came from, so calling either or both issues each heading id once. `faq` wraps each in `<details name="faq-<line>"><summary><h3 id>…</h3></summary>`: one group per block so two faqs on a page do not close each other, ids kept so the question stays a link target and the browser opens the disclosure around a fragment on its own, FAQPage schema untouched because it reads the markdown, the `.md` twin untouched because it is the source. A body with no headings renders as it did. The affordance is the second of its kind after `page.headings` (136), for the same reason: a second walk over the markdown would have got the `-1` on the second "Notes" wrong.

**164. The lightbox is a `<dialog>` the figure's own button opens, and the button is the picture.** `commandfor` / `command="show-modal"` is the platform's invoker, Baseline since late 2025; the focus trap, Escape, the backdrop and the close on an outside click (`closedby="any"`) are the browser's, and the page ships no script. The dialog's image is the figure's url, so it costs no request — a lazy image in a closed dialog is never fetched and the bytes are in the cache when it opens. The button wraps the image and `base`'s sheet takes its chrome off, so the picture is the control in every theme; its name is *View larger: <alt>*. `lightbox=false` is a prop, per image, because whether a picture is worth opening is a fact about the picture and not a site setting. The id is the block's source line, unique on a page by construction.

**165. A title's `view-transition-name` is `type-slug`, on the list's first six and on the post.** The entry list and the post's `<h1>` — the layout's or the author's `::cover` — carry the same name in a `style=""` attribute, with `view-transition-class: snypd-title` so a theme times every title in one rule; `@view-transition { navigation: auto }` (138) then morphs one into the other in Chrome and Safari, and Firefox navigates as it always has. The first six entries only: a name must be unique on its page, every named element is a group the browser captures and animates, and six is what is above the fold. Anything a slug can carry that a custom-ident cannot is folded to `-`.

**166. The build is single-threaded, on purpose, and the profile says why.** Decision 124 asked for the split before a worker pool; F1 published it (§4). A cold build is 2.6–2.9 ms an item from 100 to 10,000 pages and the parser is 74–77 % of every one of them, so the ceiling on cores is Amdahl's — four workers, 2.9 s to 1.0 s at 1,000 pages, against a 20 s budget — while the build an agent actually pays renders one route in 12.8 ms and would only pay a spawn. The number to buy is the parser's per-page cost, which is S20's report (remark vs `Bun.markdown`), and it moves the same 77 % by an order of magnitude. `profile` stays in `BuildResult` and in every report so the share is watched rather than remembered; the trigger to reopen this is `build.cold.1000` in CI past half its budget, and the answer then is still the parser before the pool.

**167. A build with drafts in it is never the site, and pushing drafts is a named act.** S19a′ left branch previews as a decision, and the decision is this. The build is branch-aware (`builtBranch`: the host's environment first, because every host builds on a detached HEAD; the checkout second; `SNYPD_BRANCH` over both), so a host that runs the same `snypd build` on `snypd/drafts` gets the drafts — and a build with drafts in it that *leaves the machine* — the branch, or `--drafts` — marks itself in every output a crawler reads: `<meta name="robots" content="noindex">` on every page with the canonical still naming production, and `Disallow: /` in `robots.txt`. `snypd dev`'s build includes the drafts and marks nothing, because decision 51 already owns it: an item page under the preview server is `dist/`'s bytes, and the S18e test that asserts so was the first thing to fail when the mark was put on every drafts build — so `drafts` (what is rendered) and `preview` (what the output says about itself) are two options on `build()`, and the second is on by default only when the first was decided by the branch. That is the whole of what a preview can promise — out of search, and out of nothing else — and the second half of the decision is that the promise is *said* rather than implied. `DRAFTS_PUSH_EXPOSES` is three sentences: every unapproved word goes to the remote, readable by whoever can read the repository; a host that builds branches serves it at its preview URL, readable by whoever has the URL; nothing is approved or published by any of it. `site` › push `preview: true` is the only way snypd sends the drafts branch, its result leads with those sentences whether it pushed or refused, and `deploy.push: human` refuses it with the `git push` a person would run — unapproved text leaving the machine is the stronger case for a person's hand, not the weaker. The Desk keeps its one button: a preview is an agent's act with a person's policy over it, and a second button would be a second gate to explain. What is not verified is the host: snypd.rocks builds with a pinned launcher this tree has not released (E3), so the bare-remote test and the environment matrix stand in until the pin moves.

**168. The parser stays, and the other engine is a row in every run.** docs/07 decision 5 asked for remark vs `Bun.markdown` measured weekly and made the switch a v0.2 spike; F1 put the parser at 74–77 % of every cold build; S20 answers the question the two of them left. `build.cold.<n>.parse.bun` runs `Bun.markdown.html` over the sources the build just parsed and reports the ratio beside F1's parse row — **CI reads 98× / 95× / 93× at 100 / 1,000 / 10,000 posts, `Bun.markdown` at 117–120 MB/s** (this box read ≈ 150×; its micromark is the slower of the two) — so what S5 measured once is watched rather than remembered. The ratio is the ceiling, not a candidate: `Bun.markdown` is a renderer with a visitor, not a parser — strings come back, not a tree; no positions, so lint's line numbers, `buildTree`'s typed blocks and `suggest_blocks`'s shapes have nothing to stand on; no directive syntax, so `:::chart` is a paragraph; and it is Bun's, on a content path docs/04 keeps runtime-neutral. The spike, when it is worth having, is the seam those four things need — a `:::` and frontmatter pre-split, a positioned tree, and one output that two engines must agree on byte for byte or E7's property splits along the runtime — and the ratio the row publishes is what that seam is allowed to cost. Inside micromark the extensions are roughly half the parse and none is dropped: `gfm`'s autolink-literal and table, and `directive`, each change what a reader's text means, and a build at 14 % of budget does not buy a fifth of its parse with a semantics change. The trigger is decision 166's — `build.cold.1000` in CI past half its budget — and the answer then is this spike, before a worker pool.


**169. Inside a subtree the site wrote into, the keys it did not touch are one counted line.** `snypd://config` had one collapse rule since S2: a subtree whose every leaf is a default folds to one line naming where the default lives, and a subtree with one non-default leaf in it is printed whole. The second half was never looked at, because no site in the repo had tripped it: the kill test with four plugins on (S21) did, by the plainest route there is — it swapped to `editorial` and retuned two tokens, which is the D1 task, and the resource grew by the theme's other thirty-eight token *declarations*, one line each, plus every budget because one was set, plus every field `release` inherits because the plugin declared three. `tokens.learn` on the site the test left read **6,529 against D4's 6,000.** The rule now is: below the second level, the keys the site (or a plugin) wrote keep their lines and provenance, and the untouched siblings become `# 38 more untouched: <theme editorial default — editorial/theme.yaml:112–167>` — a count, the family, and the line range, on one line. The first two levels stay itemised because `types.post`, `taxonomies.tag` are the names an agent navigates by, and a name there is worth its line. **6,529 → 5,654**, and the pre-run corpus 5,691 → 4,684. `tokens.learn.kill` is measured on the site the run *leaves* — the one the next session learns — and it is `exact`: a token count has no runner noise, so the line is docs/05's 6,000 and not 80 % of it, which is the S19c rule (`Metric.exact`, docs/07 §3) applied to a count that is not a clock. `tokens.learn` on the theme corpus keeps its 80 % line, unchanged, so the two rows are not confused for one.

**170. A model at the keyboard is a driver, and the record it leaves is a file, not a test.** D1's first clause is "from a fresh Claude Code session with only the MCP", and S17 ran it with a scripted route because a scripted route is what a CI runner can run. S21 runs the clause literally — `claude -p`, every built-in tool off, one MCP server, the task in a person's words (`live.ts` `KILL_PROMPT`) — and turns the session's stream into the turns `session.ts` records, so the three numbers mean the same thing whoever is at the keyboard and `scenario.ts` scores the same finished site. Two rules follow. It is *not* a test: CI has no login, a lane that passes only at Sunny's desk is not a gate, and a model's route varies by the hour — so `agent.test.ts` keeps asserting the scripted route exactly and the live runs are records under `bench/agent.claude-<model>.*`, dated, with the model id the alias resolved to. And the harness adds nothing to the task: the scripted driver's opening reads, `find_tools`, the preview a person approves on — none of it is in the prompt, because a route the prompt supplies measures the prompt. What the three found on 15 Sep 2026: **15/15 for all three**, haiku in 30 calls, sonnet 22, opus 23 against the scripted 18; every one reached a lint-clean draft in 3 calls of D1's 8 (create, a fix, lint — the first draft was never clean, and the fix was always one call); sonnet and opus both rendered a preview nobody asked for, because the tool's description says a human looks there; and the first haiku run failed its build on `Cannot find module 'react/jsx-dev-runtime'`, which was the harness running the checkout from the site's directory — the JSX import source is the cwd's tsconfig — and is fixed in the harness, with the note that a release binary carries its themes pre-bundled and never meets it.

**171. The index names a primitive; the sheet is its contract — and a prompt that plans one reads the other.** `write-post` said "read `snypd://spec/primitives`, plan the post, write it", and twenty topics × three models measured what that sentence buys: opus 0.95, sonnet 0.60, haiku 0.40 on the first lint. The failures were not prose — every one was a prop the index does not carry, because the index is short by design — it is a third of what `tokens.learn` counts against 6,000 (docs/05) — and the sheet is where `flow` says its steps have a `do:`, `diagram` says its body is YAML nodes and edges, and `stat` says its `source` is a URL or a site path. The model that passed had read eight sheets before its first `content.create`; the two that failed had read two resources and started writing. That is not a model's ceiling — it is a route the prompt left to the model's judgement, and decision 170 says a route the prompt supplies measures the prompt, so this is the prompt being measured and found short. The fix is one paragraph: read the sheet of every primitive in the plan, one read each, before a line of the body, and the sentence says why ("a first draft written from the index alone fails on exactly those, and every one of those failures is a read you skipped"). Re-run the same day: haiku 0.70, sonnet 0.95, opus 0.95, with reads before the first create at 6–7 for all three and ≈ 20 k tokens a post more on the two that had not been reading — a fair price against a failed lint, a second attempt and the tokens both cost. Two rules from it. And a lane run through `claude -p` shares the desk's rate window, so a run can end in "no attempt" rows that belong to the window, not the model — those rows are never counted as fails; `--topics=A-B --merge` re-runs the slice into the record it already has, keyed by model and topic, and the record carries every attempt's turn count so a merged row is not distinguishable from one that ran first time, because it is not different. The budget stays unset (docs/05's ≥ 0.8 is a target) until the lane has run on the release binary at least twice; haiku's remaining fails are an authoring habit — a `stat` cited with something nobody can check — and a prompt fix for that would be teaching the model to be less honest about where its number came from, which the lint exists to refuse.

**172. **173. **180. The front page is a page** (S25, 16 Sep 2026, docs/16 §2). A `page` with `home: true` renders at `/`; the list the `index` layout drew there moves to `/posts/`; the theme's `home` layout — the page layout's body, the newest six posts under it, a link to the rest — draws it, and a theme without one draws it as a page. The rest is the consequences, each chosen over its alternative: **(a)** the route is decided where every other route is decided, `listContent`, from the file's own frontmatter and only for a type that declares the field (`page` does; `post` does not pay the read), so `content_query`, the preview, a nav `ref`, lint rule 5 and an IndexNow ping all say `/` — a build-time reroute (the P2 filter's shape) would have had the site's tools calling the page `/home` while the site served it at `/`. **(b)** Two pages that ask are not an error the build throws: the first by path holds `/`, the second keeps its own route and lint rule 14 says which one won, because a build that refuses over frontmatter is a site that cannot be built by the person who can fix it. **(c)** The tab at `/` is the site's name, not the page's title; the page's title is its heading. The list at `/posts/` is `Posts`, a `CollectionPage`; `/` keeps the `WebSite` schema it always had, because to a crawler nothing about the site moved. **(d)** Turning `home` off logs a move `/` → `/welcome`, and rule 10 is silent about it: `/` is never a dead URL. Turning it on logs `/welcome` → `/`, and rule 10 asks for the redirect, because that one is. **(e)** The theme fixture carries one — six layouts is what "every layout" means now — and `bench page` treats `/posts/` as its own shape, so the `home` and `index` layouts are both under axe. (Decisions 178–179 are on the README branch, docs/08 and this file; numbering continues from them.)

**181. A clip is a `figure`, not a fourteenth primitive** (S25, docs/16 §2.1's recommendation, taken). A `src` ending `.mp4` or `.webm` renders `<video controls preload="metadata" playsinline>` with `poster` — an image, so `ctx.media` sizes it and the box is reserved the way an image's is — and the same `alt` and `caption`; `lightbox` is ignored, because the controls already have full-screen and a dialog around a second copy of the clip would play both. Nothing autoplays and nothing is fetched before play. The vocabulary stays at thirteen: a figure is *a thing the text refers to* and a clip is one; a `video` primitive would have cost a spec file, a lint rule, a base implementation, a twin fallback and every "thirteen" in the README and on the site, for the same markup. The twin is the source byte for byte (docs/01 §2), so the "fallback" is what the spec's `fallback:` line says an agent should read the directive as — `[alt](src)` — and not a second rendering.

**182. A token count is `exact`** (S25; applies S19c's own rule). `tokens.learn`, `tokens.tools` and `tokens.page.md` are counts — the same text is the same number on every runner — and docs/05 quotes their budgets in prose (6,000 · 3,000 · 2,500). CI had been holding them to 80 %, so `tokens.learn.editorial` sat at 4,779 against a 4,800 line that no document claims, and S25's forty tokens of `figure` spec — a `poster` prop and the word *clip* — would have failed the build. The alternative was to cut the spec's text to fit a number the design never set, which is the tail wagging the dog: an agent reads that resource to learn the vocabulary, and the line exists to keep the *vocabulary* small, not its explanation terse. The 6,000 is now the line, as decision 118's `font.kb` and F1's `onboard.handoff` already are; the headroom a count does not need was never headroom. Sunny can reverse this by deleting three words.

**183. The studio look is a bundled theme** (S29 · U8, 17 Sep 2026, docs/17 §7 call 1). `themes/studio/` ships in the binary beside `editorial` and `technical`, the seventh look on the gallery and on `/themes` the day it lands, held to the same eighteen gated rows. The claim in docs/17 §1 — an agency site's feel at 0 KB — is snypd's to make and the bench is what makes it; a community theme would prove that a stranger *can*, which is a later claim (E8). It is the first theme with a layout file of its own (`layouts/home.tsx`), and it reads the front page through a seam the renderer now hands every layout: `page.sections`, the body split at its `##` headings by the same walk that issues the heading ids, so a band is a `<section>` the layout wraps and a link into it still lands. Every other layout renders `body` whole and never looks.

**184. One clip per page may play by itself** (S29, docs/17 §4.2; amends 181). `autoplay: true` on a `figure` clip or a `cover`'s `media` renders `<video autoplay muted loop playsinline preload="none" poster>` — the four attributes are the renderer's, never the author's — followed by the poster as a still that `base`'s own sheet shows in place of the clip under `prefers-reduced-motion`. Lint rule 15 fails the second on a page naming the first, warns on an autoplay with no poster (nothing to show under reduced motion) and on one that names a picture. 181's reason stands for every other clip: nothing plays and nothing is fetched until a reader asks. The bound is what keeps the amendment from becoming the reference's 22 MB (docs/17 §2), and `page.media.kb` (187) is the row that would show it had.

**185. `logo-wall` is the fourteenth primitive** (S29, docs/17 §4.3; the vocabulary was locked at thirteen by docs/13 §5.4, and this is the spec minor that rule allows). A container over a markdown list of images, each optionally inside a link and followed by a caption; `layout: grid | marquee`, `title`. It is the client logos, the awards row and the badges in a footer — three of the reference's fifteen sections — and the one shape none of the thirteen carried honestly: a row of `figure`s is captions and lightboxes, a `stat-row` is numbers. Alt text is the author's (rule 4), a wall of fewer than three is rule 16, `marquee` renders the row twice with the copy `aria-hidden` so a theme can animate it and every other theme shows one. The suggester learns it (a list whose every item is one picture), and the corpus gains three posts. Every *thirteen* in the tree is *fourteen*; the README on `r0-readme-ground` is owed the same edit.

**186. S29 runs before Gate D, not after it** (17 Sep 2026; docs/17 §7 call 4 reversed by Sunny the same afternoon: *"lets work on the studio look"*). The hero film's site footage is dull because the site is dull, and the film is the README's hero on launch day — so the look comes first, then the site adopts it (owed, on 0.1.5), then the footage is re-shot. Nothing here is visible on snypd.rocks until the host builds with a release that has it; the token is still the gate.

**187. `page.media.kb` is reported, not gated** (S29, docs/17 §5). Bytes of image and video fetched on first load at the widest viewport before any scroll — the row on which the reference reads 22,900 and the studio fixture's front page reads 8.5 (6.3 KB of pictures, 2.3 KB of a two-second clip). One row in the page suite and one per look on the gallery; a budget after one measurement on CI, the way `page.bytes.kb` was treated (docs/14 §6). It is the row a stranger's theme with a showreel is held to.

**188. One edge** (S29 · U9, 17 Sep 2026, docs/18 §5). On the studio look every child of a band starts on the `wide` track — the band's title, its prose, its numbers, its cards — and prose is limited by `--measure`, never by an indent. Amends docs/17 §3's "text, breakout, full" for the front page only; a post keeps the reading column. It was the audit's first finding: two left edges down the whole page, the title indented past its own content on a tablet. The same rule reaches a list page, whose title sits over a grid of cards. No markup changed.

**189. Depth is the renderer's** (S29 · U9, docs/18 §2 · 2). A primitive that emits a heading for its title takes the level from the section it sits in: the walker hands every block `depth` — 1 before the page's first `##`, 2 under one — and `steps` and `faq` emit `h{depth + 1}`. So "How we work" and its "Four stages, one room" are a heading and a sub-heading (WCAG 1.3.1), not two headlines, and the outline of the Ferrule front page is one `h1`, four `h2`, one `h3`. No `level` attribute exists or will: the alternative is exactly the kind of thing docs/18 §3 refuses — a word an agent has to discover by looking. Posts change where a block sits under a `##`, which is the right change; `editorial` and `technical` follow with one selector each.

**190. The motion control** (S29 · U9, docs/18 §2 · 7). A page with an autoplaying clip or a marquee carries one visible stop control — a checkbox and the word "Motion" — rendered by `base`'s sixth part (`parts/motion.tsx`) on those pages and on no other, placed by the theme (studio: a pill in the masthead). `base`'s sheet swaps the still in for the clip on `#snypd-motion:checked`; studio stops its marquee and its reveals on the same selector. WCAG 2.2.2 asks that moving content which starts on its own and runs past five seconds can be paused by everyone, not only by a reader whose system asks for reduced motion; `prefers-reduced-motion` stays the default for those readers, and the control is hidden for them because it would pause what is already still. Per page, no memory — the criterion asks for the mechanism, not persistence. Zero JS.

**191. A front page has a recipe** (S29 · U9, docs/18 §3 item 4). `snypd://spec/home` is the agent's one-screen answer to "what goes on the front page": a `cover`, one block, three to five `##` sections of one block and at most one paragraph each, the entries band the theme's — and the Ferrule home as the worked example, embedded. Two lint rules make the recipe checkable in a sentence rather than a screenshot: 17 *hero-too-tall* (a second block before the first `##` on a `home: true` page, named and told where to go) and 18 *duplicate-title* (a block's `title` that repeats or restates its `##` heading). The theme fixture's own front page moved its numbers into the first section to pass 17. `snypd init` scaffolding the recipe's example is owed, with the specimen's `examples/` directory (docs/18 §6 call 3).

**192. A block's title is the author's** (S29 · U10, docs/19 §2 · 3). No primitive carries a default title in the spec: `faq`'s *FAQ* was the last, and it rendered a heading the author never wrote — a blog's label between a section's heading and the questions under it, the same word docs/18 removed from `tldr`. A `faq` with no `title` renders no heading of its own; the section's is enough. Given one, the questions render one level under it (`h{title + 1}`) so the outline nests (WCAG 1.3.1) while the author keeps writing `###` — the level is the renderer's (189), never a word an agent has to know. The FAQPage schema and the `.md` twin read the markdown and see neither change. Goes for every theme, because it is the spec's default and not a sheet's.

**193. Lint walks what the build reads** (S29 · U10, docs/19 §2 · 5). A taxonomy term's file belongs to no type, so `listContent` never opened it, `readFrontmatter` returned `{}` when its YAML failed, the term showed its slug on every post and its own page, and `snypd lint` said *0 errors* — the one mistake on the specimen that no sentence anywhere named. Rule 19, `frontmatter-unparsed`: every `content/taxonomies/<taxonomy>/*.md` is opened once and a frontmatter that does not parse is an error at the file's line — the parser's line plus the fence — with the hint the case needs (*quote the value on line 4*; a colon in an unquoted value is a nested mapping to YAML). Rule 0 says the same line and hint for a post. A rule that fires is worth less than a rule that says what to type: the sentence is the deliverable, and it is checked to fire exactly once over four corpora, on the finding.

**194. Every dated type has an archive** (S29 · R1, docs/20 §3 · 1, 18 Sep 2026). A type with a layout and a `date` field lists at the directory of its url pattern — `/posts/` for `post`, `/work/` for a `work` — unless a page holds that route, rendered through `<type>-index` when the theme declares one and `index` otherwise, a `CollectionPage` like a term's, keyed on that type's entries alone. It is headed by the site's own word for the type when a menu links it (the header's first, then any location), else the plural of its name: the rule the studio's front page already used for its entries band (docs/18 §2 · 10), now the page's title. The list at `/` stays every dated type newest first while no page holds `/`; when one dated type is all a site has and `/` is free, `/` *is* its archive and no `/posts/` appears — a blog built before this decision builds byte for byte after it (the `registry-blog` fixture proves it; the S25 fixture's `/posts/` is this rule's first case, not a special one any more). `nav.ts` resolves a `ref` against the same `typeArchives`, so *Work → /work* is a live menu item the day the type is declared. WordPress's `archive-work.php`, as a rule and not a file.

**195. The front page lists one type** (S29 · R1, docs/20 §3 · 2). The `home` layout's entries are the newest six of the type whose archive the header menu links first — *Work* on a studio, *Posts* on a blog — and of the first dated type declared when the menu names none; the layout is handed the archive (`LayoutProps.archive`: type, route, title) and links it, so `base`'s *Latest posts* and the studio's band point where the entries came from. Until now it was the newest six of every dated type, which on every site so far was the same list. A site with cases beside notes wants its front page to show the cases, and its masthead already says which. docs/20 §3 · 2 had *every dated type when the menu names none*; one type is the simpler rule and the one whose link is never wrong.

**196. Schema follows `extends`** (S29 · R1, docs/20 §3 · 3). The resolved type keeps the name of the type it extends (`types.work.extends = "post"`; `typeLineage` walks it), and `pageSchema` reads the lineage: a type that extends `post` is a `BlogPosting`, one that extends `author` a `Person`, everything else a `WebPage`. docs/02 §1 sketched `caseStudy` as an article about work; until now it emitted a `WebPage` because the emitter matched the type's name. The changelog plugin's `release` was the first to benefit — it extends `post` and now says so in its JSON-LD. `client → sourceOrganization` from docs/20 §3 · 3 is *not* done: a field's name is the site's, and a renderer that knew one by name would be guessing. R3 decides whether the work layout emits it from the type's declaration.

**197. A type renders through its base type's layout where the theme has none** (S29 · R1, docs/20 §3 · 4). `types.<t>.layout` names a layout; when the theme has no file by that name the build falls to the layout of the type it extends, then that one's, then `post` — WordPress's `single-work → single → singular`, as a decision — and says so on the build line (*work renders through `post` — editorial declares no `work` layout*; `BuildResult.fallbacks`). Only a type with nothing left to fall to is the refusal a missing layout always was; an explicit `layout:` in a file's frontmatter that the theme lacks is still refused, because that one is the author's word. `check theme` gains `coverage.layouts`: the layouts a theme declares beyond the six, so *what does this theme do with a `work`?* has an answer before a build asks. The six-layout contract does not grow: a theme that draws `/work/` as cards declares `work-index` beside its six and nothing else changes.

**198. A listed entry carries its terms; a dated item knows its neighbours** (S29 · R3, docs/21 §1). `Entry.terms` is on every entry a list hands a theme — in the order of the type's taxonomies, from the same `termsOf` the page uses — so a card can say *Product* without knowing which field held it, and a theme that read `frontmatter.category` for the word stopped guessing. `LayoutProps.adjacent` is the item before and after in its type's list, newest first, for a content route of a dated type: what a *next case* card draws from. Both are in the key: a term's title is in every list key, and a case re-renders when the one after it is published — one more page per edit (the fixture's count went from 13 to 14), which is the incremental cache being right.

## 10. Open questions — the calls that are Sunny's

1. **The npm credential: a new token now, or trusted publishing now?** The token is five minutes and
   expires again; trusted publishing is twenty and does not. Recommended: the token to unblock 0.1.4
   today, trusted publishing in the same session that touches the supply-chain rows (finding 9).
2. **Raw HTML: `warn` or `refuse` by default?** Decision 122 says `warn`. `refuse` makes the claim
   absolute and annoys the first person who wants an embed.
3. **Does the GitHub name matter enough to chase?** `github.com/SNYPD` is a dormant 2023 user account, so
   the org name is not available. Options: a suffixed org, a name-release request to GitHub, or stay on
   the personal account and let the domain carry the brand. One email, not a blocker.
4. **Trademark before or after launch?** MIT gives away everything except the name. Before is cheaper to
   argue; after is cheaper to afford.
5. **Do we keep shipping a Bun runtime to people who already have one?** I0 measured it: the release
   binary is 83.85 MB, a one-line program through the same recipe is 78.71 MB, and **snypd is 5.14 MB of
   it — 6 %**. So 37 MB crosses the wire for the person, and 37 MB again for the host on every deploy,
   and ~94 % of it is a second copy of the runtime that `bunx` proves is already installed. The fix is not
   an optimisation, it is a distribution shape: `@snypd/cli` stops listing the five binaries as
   `optionalDependencies`, ships the bundle instead (~5 MB), runs it on a `bun` it finds, and fetches a
   binary on first run only for a machine that has none. **The cost is the thing S18d′ bought:** today
   every byte arrives through npm with provenance, in one resolution, and works offline after it. A
   first-run fetch is a second trust story and a second failure mode. Recommended: not before launch —
   the number is now measured and the row is in `bench/latest.md`, which is enough to decide it later with
   evidence rather than now with a deadline.
6. **May `init` write a durable path into `.mcp.json` instead of `bunx`/`npx`?** Branch 2 exists because
   the file is committed and a clone on another machine is its second reader (docs/08 §12.8, F5). The
   cost of that portability is **+240 ms per session on `bunx` and +2.2 s on `npx`** — against a D2 budget
   of 50 ms for the whole cold start — plus the case nobody has hit yet: a collected cache puts a 37 MB
   download in front of `initialize`, with no error on any surface. Hardlinking the running binary into
   `~/.snypd/bin/snypd-<version>` costs 0.1 ms on one filesystem and 1.0 s across two, and takes session
   start to 25 ms. It breaks the clone. Options: take the trade and have `site` › doctor repair a clone;
   keep branch 2 and accept the seconds; or write the durable path *and* teach doctor to rewrite it —
   which is the two-reader problem solved rather than chosen between, and about a session of work.
7. **No reader-side theme toggle — as a decision, not an omission** (docs/14 §7, call 2). `light-dark()`
   follows the OS and a variation is the *site's* choice; a toggle that outlives the page needs storage,
   storage needs a script, and the 0 KB claim comes first. It is the second most common piece of
   well-meant advice the launch will get, and the answer is better written before it is asked.
   Recommended: decide it, in the spirit of 145.
